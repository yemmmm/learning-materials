## 第 1 页：本体论如何帮助 Agent 理解与处理业务

预计用时：0.5 分钟

### 屏幕文字

**本体论如何帮助 Agent 理解与处理业务**

以 Ontology Platform 项目为例

贯穿案例：工业设备售后服务

### 呈现形式

简洁封面。标题占主体，副标题与案例名称放在下方。背景采用淡化的业务概念关系图，避免技术术语和密集节点。

### 讲解备注

今天关注 Agent 如何获得业务依据。先认识 Agent 与本体，再看项目如何把业务知识组织起来，最后用一张服务工单说明实际应用路径。

## 第 2 页：Agent 怎样完成一个任务

预计用时：1.5 分钟

### 屏幕文字

**Agent 围绕目标使用工具，并根据结果继续工作。**

- 大语言模型：理解请求、分析信息、组织回答。
- 工具：查询数据库、读取资料、调用业务接口。
- 上下文：处理当前任务时能够看到的要求、知识和结果。
- 反馈：工具结果帮助 Agent 决定下一步。

任务示例：“帮我分析服务工单的处理情况。”

### 呈现形式

一张任务流程图：用户请求、Agent、工具、结果反馈、回答。工具与 Agent 之间画往返连接，逐步出现各环节。

### 讲解备注

可把 Agent 理解为一个会使用工具的工作助手。它可以先查询工单，再读取合同信息，遇到缺失内容时继续查询或提问。工具调用次数和执行步骤因任务而异。

概念来源：[Anthropic：Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)。

## 第 3 页：业务任务需要明确的业务含义

预计用时：2 分钟

### 屏幕文字

**“这张工单满足 SLA 吗？”**

回答前，需要明确：

- SLA 指响应、到场、恢复，还是解决时限？
- 哪份合同、哪种严重度决定适用目标？
- 从哪个时刻计时？暂停和空值怎样处理？
- 所需定义和数据分别在哪里？

页面落点：**业务口径决定数据怎样解释。**

### 呈现形式

中央放一个工单问题。周围分布合同条款、业务手册、数据库字段和接口说明四种材料，用连接线标注各自提供的信息。

### 讲解备注

SLA 是服务水平协议，通常约定服务质量或时间目标。例如，同样写着“4 小时”，可能指首次响应，也可能指恢复服务。计时和适用条件不同，最终结论就可能不同。这里的问题来自案例中需要业务确认的内容，不预设实际口径。

案例来源：[工业服务场景摘要](https://github.com/yemmmm/ontology-platform/blob/main/docs/evaluation-scenarios/industrial-service-v3/modeling-input/scenario-brief.md)。

## 第 4 页：帮助 Agent 完成业务任务的几种方法

预计用时：2 分钟

### 屏幕文字

| 方法 | 主要做什么 | 工单场景中的例子 | 需要关注什么 |
| --- | --- | --- | --- |
| 提示词工程 | 用指令和示例引导任务处理 | 要求先核对合同，再回答 SLA 问题 | 业务要求是否表达清楚，模型是否遵循 |
| 常见文档 RAG | 检索资料，供模型参考 | 找到合同条款与服务手册片段 | 是否找到完整、适用的材料 |
| 模型微调 | 用训练样本调整模型，使其适应任务 | 训练工单分类或固定输出格式 | 训练样本、更新与效果验证 |
| 本体 | 显式组织业务定义、关系与语义约定 | 连接工单、合同、严重度和 SLA | 定义是否正确，关系是否完整 |

**这些方法各有侧重，实际系统可以组合使用。**

### 呈现形式

全页使用一张四行对比表。突出“主要做什么”一列。按行依次出现，不使用优劣排名、升级阶梯或勾叉评分。

### 讲解备注

RAG 可简单解释为“先查资料，再根据资料回答”。微调可理解为“用样本训练模型适应某类工作”。此处对比常见的文档片段 RAG；RAG 也可以读取结构化知识或本体。本体提供的定义和关系，同样需要通过检索或工具送入 Agent 的上下文。检索、模型训练和形式推理是不同机制；形式推理结论需要相应公理、事实和推理器支持。

来源：[RAG 原始论文](https://arxiv.org/abs/2005.11401)、[LoRA 论文中的任务适配方法](https://arxiv.org/abs/2106.09685)、[W3C OWL 2 Primer](https://www.w3.org/TR/owl2-primer/)。

## 第 5 页：本体表达业务领域中的概念与关系

预计用时：1.5 分钟

### 屏幕文字

**本体（Ontology）明确描述一个领域中的概念、关系及语义约定。**

可以先把它理解为一张带有定义的“业务概念地图”。

- 工单是什么？
- 工单与故障、设备、合同怎样关联？
- SLA 的含义和适用范围是什么？
- 哪些知识已确认，哪些仍待澄清？

### 呈现形式

左侧放简短定义，右侧放五个概念组成的小图。每条连线标明含义，节点旁只保留一行说明。

### 讲解备注

这里讨论计算机领域的本体。业务概念地图只是入门比喻；采用形式化语言表达公理时，本体还可以支持逻辑推理。清晰的自然语言解释与明确的结构关系可以共同帮助使用者理解业务。

概念来源：[W3C OWL 2 Primer](https://www.w3.org/TR/owl2-primer/)。

## 第 6 页：本体中的几种基本表达

预计用时：2 分钟

### 屏幕文字

| 表达 | 简单解释 | 教学例子 |
| --- | --- | --- |
| 概念／类别 | 业务中讨论什么 | 设备、工单、服务合同 |
| 属性 | 某项内容具有哪些信息 | 工单状态、设备型号 |
| 关系 | 不同内容怎样关联 | 工单处理故障，合同覆盖资产 |
| 分类 | 哪些类别具有包含关系 | 泵是设备的一类 |
| 业务条件与口径 | 在什么情况下怎样判断 | SLA 的适用条件与计时口径 |
| 未知与范围 | 哪些内容尚未确认或仅局部适用 | 暂停时间是否扣除待确认 |

### 呈现形式

采用一张六行表，右侧教学例子依次出现。不同表达使用少量颜色区分，避免介绍代码语法。

### 讲解备注

分类和普通关联需要区分。“泵属于设备类别”与“工单处理故障”表达的关系不同。业务条件可以先以普通业务知识保存；是否采用可执行规则或形式公理，取决于实际需要。项目中的每个名词也不必都成为正式 Class。

项目依据：[v4.0 需求 R4.0-002](https://github.com/yemmmm/ontology-platform/blob/main/docs/requirements/requirements-v4.0.md)。以上例子为教学示意。

## 第 7 页：本体、知识图谱与数据库的分工

预计用时：1.5 分钟

### 屏幕文字

| 内容 | 主要关注 | 例子 |
| --- | --- | --- |
| 本体 | 概念含义、分类和关系的约定 | 什么是工单，如何关联故障和合同 |
| 知识图谱 | 用图组织实体、关系及相关知识 | 以节点和连线表示已表达的知识 |
| 数据库结构 | 数据的表、列、键与连接 | 工单表、合同表、时间字段 |
| 业务数据 | 实际发生的业务记录 | 某张工单的报修与恢复时间 |

**本项目：本体保存语义和映射，实际业务行保留在外部数据库。**

### 呈现形式

上半页用表说明分工，下半页用“语义模型”和“业务数据库”两块区域表达映射关系。不要画成所有业务行迁入本体。

### 讲解备注

本体和知识图谱可以结合，数据库结构也可以成为建模线索。需要同时区分一般技术能力和本项目的选择：本体技术可以表达具体个体，但当前关系型业务场景把实际业务行保留在源数据库。

来源：[W3C RDF 1.1 Concepts](https://www.w3.org/TR/rdf11-concepts/)、[工业服务场景摘要](https://github.com/yemmmm/ontology-platform/blob/main/docs/evaluation-scenarios/industrial-service-v3/modeling-input/scenario-brief.md)。

## 第 8 页：自动推理识别知识中的隐含结论

预计用时：2 分钟

### 屏幕文字

**教学示例**

已知：

1. 离心泵是泵的一类。
2. 泵是设备的一类。

可推出：**离心泵是设备的一类。**

本体自动推理可以用于：

- 推导隐含分类和关系。
- 检查形式化定义的逻辑一致性。
- 为查询提供符合公理的语义结论。

**平台状态：后续能力，当前阶段不提供。**

### 呈现形式

两个已知分类关系放在左侧，推理器放在中间，推导结论放在右侧。最后用虚线补出原图中未直接画出的分类关系。仅播放教学动画，不展示伪造的系统推理回执。

### 讲解备注

这里的“推理”指由形式公理和事实得到逻辑蕴含。它与大模型生成分析不同。它也不能直接代替业务服务计算 SLA、金额或聚合指标。OWL 通常采用开放世界语义，缺少某个结论并不意味着它为假。后续接入推理器时，需要实际建模、正确公理和推理验证。

来源：[W3C OWL 2 Overview](https://www.w3.org/TR/owl2-overview/)。当前平台状态依据：[R4.0-025](https://github.com/yemmmm/ontology-platform/blob/main/docs/requirements/requirements-v4.0.md)；“后续能力”为本次演示要求的方向标记。

## 第 9 页：本体怎样帮助 Agent 工作

预计用时：1.5 分钟

### 屏幕文字

| 应用 | 本体提供的业务依据 | Agent 的工作 |
| --- | --- | --- |
| 业务问答 | 定义、范围、关联条件 | 解释问题并组织回答 |
| 数据分析 | 指标口径、数据映射、连接含义 | 生成或检查查询，再分析数据 |
| 任务与工具选择 | 动作含义、条件、外部能力描述 | 判断步骤并选择适用工具 |
| 多 Agent 协作 | 可共同引用的业务定义 | 围绕同一份知识分工处理 |

### 呈现形式

采用三列表格。每行只放一个例子，不列产品名称或代码。突出“本体提供”和“Agent 使用”之间的分工。

### 讲解备注

例如，一个 Agent 负责解释 SLA，另一个负责组织 SQL。它们应当引用同一份已确认口径。共享模型提供共同依据，仍需要检验 Agent 是否正确理解和使用。表中描述应用方式，不代表本项目所有端到端场景均已验收。

## 第 10 页：提示词、检索、本体与工具怎样配合

预计用时：1.5 分钟

### 屏幕文字

围绕一个业务请求，各部分分别提供：

- **提示词**：任务要求、处理步骤和输出约定。
- **资料检索**：相关制度、手册和说明材料。
- **本体检索**：业务定义、显式关系、适用范围和映射。
- **业务工具**：查询实际数据，或执行获准业务动作。
- **Agent**：结合这些输入，分析并输出结果。

### 呈现形式

画一张整合信息流图。把资料、本体和业务工具放在 Agent 周围，标明各自传递的内容。检索结果进入上下文，工具结果返回 Agent。

### 讲解备注

读取本体也是一次工具或检索操作。任务需要什么，Agent 就获取什么；简单任务可以省去不必要的步骤。正式接入自动推理后，推理结论也需要通过明确的读取接口供 Agent 使用。

## 第 11 页：Ontology Platform 的整体定位

预计用时：1.5 分钟

### 屏幕文字

**面向 Agent 的业务语义平台**

平台连接：

1. 业务资料与人员确认。
2. 建模 Agent 产生的语义模型。
3. 按权限读取模型的消费 Agent。
4. 保存数据、执行动作的外部系统。

核心职责：**保存业务语义，提供确定性写入与受治理读取。**

### 呈现形式

使用一张分层架构图：资料与业务人员、建模 Agent、平台、消费 Agent、外部数据库/API。平台内部只列“语义模型、写入检查、权限、检索”四项。

### 讲解备注

消费 Agent 指使用模型完成任务的 Agent。平台返回模型内容和状态，Agent 负责解释业务问题。API 可以简单解释为软件访问其他服务的入口。项目中的业务数据库与平台控制状态数据库是不同职责，图上需要标清。

项目依据：[v4.0 需求的范围与边界](https://github.com/yemmmm/ontology-platform/blob/main/docs/requirements/requirements-v4.0.md)、[v3.0 关系型语义场景要求](https://github.com/yemmmm/ontology-platform/blob/main/docs/requirements/requirements-v3.0.md)。

## 第 12 页：同一业务模型的七个视角

预计用时：2 分钟

### 屏幕文字

| 视角 | 关注的问题 | 工单教学示例 |
| --- | --- | --- |
| 对象 | 业务中有什么 | 工单、设备、合同 |
| 行为 | 可以做什么 | 关闭工单 |
| 规则 | 满足哪些业务条件 | 允许关闭的条件 |
| 角色 | 谁负责或参与 | 服务人员、审核人员 |
| 流程 | 工作怎样衔接 | 受理、处理、验收 |

### 呈现形式

左侧展示七行表，右侧突出一个共享“工单”节点，分别连接各视角的简短示例。可按“对象、业务活动、系统连接”三个步骤出现。

### 讲解备注

七个视角是分析业务的关注点，不要求七个 Agent，也不要求七个 Ontology。具体角色和流程名称只是教学示意，以真实业务确认结果为准。同名内容只有在含义和范围一致时才共享定义。

项目依据：[R4.0-002、003、004、010、011](https://github.com/yemmmm/ontology-platform/blob/main/docs/requirements/requirements-v4.0.md)。

## 第 13 页：业务知识怎样进入平台

预计用时：2 分钟

### 屏幕文字

1. **业务澄清**：确认术语、范围、口径和未知。
2. **语义建模**：组织概念、关系、业务条件和映射。
3. **协同审核**：检查共享定义、关联和待确认内容。
4. **确定性写入**：先检查，再应用批准内容。
5. **实际消费与独立验证**：读取模型，用业务问题检验效果。

职责提示：**Agent 作业务判断，平台检查写入合同。**

### 呈现形式

采用泳道图，分别标明业务人员、建模/协同角色、写入角色、平台、独立消费与评判。用步骤顺序表达依赖，不固定角色数量。

### 讲解备注

dry-run 可解释为写入前的预检查，apply 是正式应用。它们检查请求、引用和资源完整性，不能证明业务含义正确。平台给出可修正反馈后，Agent 应能继续同一目标。独立语义验收需要依据真实读取与问题回答另外判断。

项目依据：[R4.0-007、009、025](https://github.com/yemmmm/ontology-platform/blob/main/docs/requirements/requirements-v4.0.md)。

## 第 14 页：消费 Agent 如何读取相关业务知识

预计用时：2 分钟

### 屏幕文字

**Context Query：取得相关语义内容和关联上下文。**

一次读取可提供：

- 主命中：最直接相关的定义或资源。
- 关联上下文：连接它的对象、条件、流程或映射。
- 读取状态：分页、截断与继续读取信息。

读取遵循当前身份的授权范围。

### 呈现形式

用一个“SLA”主命中节点和周边合同、严重度、指标口径、映射节点构成示意图。旁边放一份简短的结构化结果示意，避免原始 JSON 和内部标识。

### 讲解备注

受治理读取可以理解为“按身份和权限取得可见内容”。平台返回结构化上下文，由消费 Agent 组织最终回答。当前页面未返回某项知识，可能与范围、分页或模型内容有关，需要根据读取状态继续判断。完成读取也不等于业务知识已经完整。

项目依据：[R4.0-008](https://github.com/yemmmm/ontology-platform/blob/main/docs/requirements/requirements-v4.0.md)、[R4.3-008—012](https://github.com/yemmmm/ontology-platform/blob/main/docs/requirements/requirements-v4.3.md)。

## 第 15 页：当前能力与后续能力

预计用时：1.5 分钟

### 屏幕文字

| 当前能力 | 后续能力 |
| --- | --- |
| 多视角语义表达与共享定义 | **自动推理** |
| 确定性写入与基础合同校验 | 隐含分类与关系的语义蕴含 |
| 按授权范围读取与上下文检索 | 形式化公理的一致性检查 |

两列平铺。当前能力使用实线，后续能力使用虚线和明确文字标记。突出自动推理，避免用进度百分比或时间轴暗示已有实施计划。

### 讲解备注

当前能力描述功能范围，各项真实业务效果仍按实际验收范围判断。后续自动推理需要形式化建模与正确公理，并验证推理结果和读取方式。业务计算、脚本执行和实际动作仍由适当的外部系统承担。这一页的未来标记来自本次演示要求，不表示已开始接入推理功能。

## 第 19 页：Agent 怎样依据模型回答问题

预计用时：1.5 分钟

### 屏幕文字

用户问题：**“怎样判断这张工单是否满足 SLA？”**

Agent 的处理示意：

1. 读取 SLA 的定义、适用范围和计时口径。
2. 找到合同、严重度和业务数据映射。
3. 对未取得的信息继续查询或提问。
4. 区分已知条件、待确认项和所需数据。

回答示意：

> 需要先确定适用合同、资产覆盖和严重度目标，再按已确认口径取得开始、结束及暂停数据。目前缺少适用目标或计时信息时，保留待确认状态。

### 呈现形式

采用三列顺序展示：用户问题、读取到的语义依据、回答示意。中间内容按“适用条件、计时口径、信息缺口”分组。页脚标“教学示意”。

### 讲解备注

这里只展示回答过程与结构，不虚构一张实际工单的数值结论。独立验收应核对 Agent 是否取得了相关定义、是否正确解释、是否处理信息缺口，而不是只看回答是否流畅。

## 第 20 页：语义知识怎样连接 SQL 和 API

预计用时：1.5 分钟

### 屏幕文字

| 语义层提供 | 外部系统完成 |
| --- | --- |
| 指标定义、计时口径和数据映射 | 查询实际业务行，按确认口径计算 |
| 业务动作、条件和接口映射 | 通过获准接口执行实际动作 |

Agent 在执行前取得适用语义，执行后读取结果并组织说明。

**本页为应用路径示意，SQL/API 端到端质量按实际范围验证。**

### 呈现形式

采用两条泳道：上方为语义定义与映射，下方为外部数据查询／业务动作。Agent 位于两条泳道之间。底部简洁标注示意范围，不展示虚构 SQL 结果或成功接口回执。

### 讲解备注

SQL 用来向数据库查询数据，API 用来访问外部服务。语义映射告诉 Agent 数据或能力如何对应业务含义。语义知识权限与数据库行列权限分别由各自系统控制。模型描述动作不会自动获得外部执行授权。

## 第 21 页：适用场景与落地原则

预计用时：1.5 分钟

### 屏幕文字

本体值得考虑的业务特点：

- 多个系统使用不同名称或业务口径。
- 定义、规则和关系需要反复复用。
- 多个 Agent 需要共享业务依据。
- 回答需要说明条件、范围与未知。

实践起点：**选一个代表性问题，确认必要知识，检验 Agent 的实际使用，再逐步扩展。**

评价重点：业务含义是否正确、知识是否取得、Agent 是否正确使用。

### 呈现形式

左侧列适用特点，右侧用一条简短实践路径说明推进方式。底部放评价重点，不使用未经验证的效率或准确率数字。

### 讲解备注

简单、单一且知识变化少的任务可以先从清晰提示词与资料检索开始。引入本体要解决已经观察到的语义问题，并承担维护成本。自动推理的后续价值也要通过具体任务和正确公理验证。

## 制作与演讲建议

- 页面显示短句与图表，细节留在讲解备注中。
- 本体、工具、上下文、RAG、SLA、SQL、API、Context Query 首次出现时给一句简短解释。
- 正文不展开 RDF、SPARQL、OWL 语法、SHACL 或内部运行字段；技术交流时再解释。
- 示意图、示意回答和应用路径保留相应标识。采用真实截图时，核对版本与范围，并遮蔽凭证和无关信息。
- 自动推理在概念页介绍其价值，在平台页标为后续能力；Agent 分析和业务计算使用不同名称。
- 不依赖临场启动建模、查询数据库或执行 API。可用逐步出现的静态图完成演示。
- 若只有 30 分钟：第 6、7、12、14、17 页各压缩 1 分钟；保留方法对比、自动推理及案例主线。
