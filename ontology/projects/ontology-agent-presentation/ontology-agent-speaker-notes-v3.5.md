## P01 本体与 Agent

大家好，今天我们聊一个名字听起来有些抽象，但在业务里很具体的话题：本体，以及它怎样帮助 Agent 理解和处理业务。

我们先从一张差旅申请开始。员工提交了申请，问助手：“这张单应该找谁审批？”看起来只要找出一个名字就行。但真正往下做，就会遇到几个问题：这里说的“领导”，是直属主管，还是部门负责人？应该按哪条政策找？这个人现在还是负责人吗？

我们平时能顺利处理这些问题，是因为脑子里已经有了一套对业务的理解。今天我们要讨论的，就是怎样把这种理解明确下来，让软件和不同的 Agent 也能共同使用。

接下来，我们先看什么是本体，再看看它与大模型怎样配合，最后介绍 OntoWeave 怎样支持这份业务知识的构建和使用。我们就沿着这张申请，一步一步往下走。

## P02 张三的差旅申请，该由谁审批？

这张申请的申请人是张三。张三属于研发部，研发部的负责人是李敏，张三的直属主管则是王强。这几条信息都成立，但它们代表的关系不同。

我们再看政策：这类申请，由申请人当前所属部门的负责人审批。这里已经告诉我们应该怎么找：先找到张三所属的部门，再找到这个部门的负责人。所以，这次应当由李敏审批。

王强虽然也是张三的领导，但“直属主管”这条关系并不符合本次政策。假如政策改成“由直属主管审批”，答案就会变成王强。人员没变，组织信息也没变，改变的是政策指定的关系。

这个例子说明，我们要交给 Agent 的，除了几个名字，还包括这些名字之间到底是什么关系，以及当前问题应该使用哪一种关系。把这些含义说清楚，就走到了本体所关心的问题上。

## P03 本体：对领域语义的明确建模

在知识工程里，我们可以把本体理解为：对一个领域中的概念、关系，以及它们的语义约定，进行明确的建模。

这句话稍微展开一下。先说概念。员工、部门、差旅申请，这些词分别指什么？再说关系。谁提交了申请，谁属于哪个部门，谁负责这个部门？最后是语义约定，比如经理是一类员工，部门负责人应该是员工，本次审批要使用当前所属部门的负责人。

大家可能会说，这些东西我们本来就知道。对，但不同的人未必知道得一样。有的人一听到“领导”就想到直属主管，有的人想到部门负责人。只要这份含义没有明确下来，信息即使查得很全，也可能用错。

本体的价值，就是让这些理解有一个可以共同引用的表达。我们不必一开始就描述整个企业，只需要先把当前问题依赖的概念、关系和条件讲清楚。

理解到这里，还需要分清一件事：业务本身、我们建立的模型，以及保存模型的技术，是三个不同层次。

## P04 现实世界、本体、形式表达

请大家从左往右看。

左边是现实世界。张三确实提交了一张申请，李敏在某个时间担任研发部负责人。这些是业务中发生的事情，它们会随着人员调动和组织变化而改变。

中间是本体。我们从现实中选出与任务有关的内容，明确什么是员工，什么是部门，什么叫所属部门，什么叫负责人，以及审批政策怎样使用这些关系。这里做的是对业务的理解和抽象。

右边是形式表达。前面确认的含义，需要用软件能够处理的方式记录下来，才方便保存、交换、查询和计算。RDF、OWL 就属于这一层相关的技术。

比如，“经理是一类员工”这条含义，我们可以先用自然语言讨论清楚，再用形式语言表达。业务含义与它的编码方式有关联，但不能直接画等号。因此，理解本体时，我们首先关注的是要表达什么，然后才选择用什么技术表达。

顺着这个区分，下一页我们就来看看 RDF 和 OWL 各自做了什么。

## P05 RDF 与 OWL 分别做什么

先看 RDF。它用一种很简单的结构记录陈述：谁，通过什么关系，连接到谁或者什么值。比如，“张三，所属部门，研发部”，就是一条陈述。“研发部，负责人，李敏”，又是一条陈述。

这两条陈述共享了“研发部”这个对象，于是就连成了一条路径。很多这样的陈述连接起来，就形成了图。屏幕左边的代码，只是把这两句话写成一种具体格式，今天不用记语法，理解这个结构就够了。

再看 OWL。它可以为本体声明赋予明确的逻辑含义。例如，我们声明“经理是一类员工”，或者声明“员工和部门是互斥的类别”。支持这些语义的工具，就能进一步计算哪些结论成立，哪些陈述存在矛盾。

所以，RDF 帮我们把陈述连接起来，OWL 帮我们表达更明确的逻辑语义。它们可以配合使用。具体能推导到什么程度，还取决于模型表达了什么，以及采用了什么工具。

围绕 RDF 和 OWL，还有一些经常一起出现的技术。我们先用一页认识它们各自解决什么问题，再回到本体模型本身。

## P06 相关技术速览：词表、规则、服务与查询

除了刚才的 RDF 和 OWL，还有这四个常见名字。大家先按用途记就可以。

SKOS 用来组织概念词表。比如，我们把“差旅”作为规范名称，把“出差”记作别名，再关联“国内差旅”这样的下位概念。这样，不同说法就有了统一的参照。

SWRL 用来把“如果……那么……”的规则与 OWL 本体结合。例如，在条件齐全时，根据所属部门和部门负责人关系，表达对应的审批人规则。真正执行时，需要支持这类规则的工具。

OWL-S 用本体描述服务。比如一个“查询审批人”的服务，需要什么输入，会给出什么输出，以及怎样调用。这些描述可以帮助服务的发现与组合。

SPARQL 用来查询 RDF 图。如果图里已经有相关事实，就可以按关系模式沿着申请、申请人、部门、负责人去查找答案。

简单记就是：词表、规则、服务描述和图查询。实际项目按需要选择。现在对这些表达技术有了一个整体印象，我们回到本体模型，看看它通常包含哪些内容。

## P07 本体的常见组成

这张图里，我们可以看到本体常见的五类内容。

第一类是类，也就是概念和类别。员工、经理、部门，都属于这一类。第二类是属性，用来描述对象的特征，比如员工的姓名和入职时间。

第三类是关系。比如员工隶属于部门，它说明不同对象怎样联系起来。在 OWL 里，这种对象之间的关系通常也属于属性，我们这里把它单独拿出来，是为了便于理解。

第四类是公理。这个词听起来很数学化，在这里可以先理解为具有明确逻辑含义的知识声明。比如“经理是一类员工”，就说明了两个类别之间的包含关系。

第五类是个体，也就是具体对象。张三是一个具体的人，研发部是一个具体部门。这里有个容易混淆的地方：“经理是一类员工”，说的是类别之间的关系；“张三是员工”，说的是某个具体对象属于哪个类别。

这些是常见组成，实际建模时按用途选择。关键是表达清楚，而不是把每一种元素都凑齐。接下来，我们用其中的分类和互斥声明，看一看形式语义能带来什么。

## P08 形式语义怎样支持推理与检查

先看左边。我们已经知道两件事：经理是一类员工，李敏是经理。这两条知识放在一起，就能推出“李敏是员工”。虽然我们没有单独写下这句话，但它已经包含在前面的逻辑关系里了。

再看右边。假设我们已经明确规定，员工和部门是互斥的类别。原来只记录“张三是员工”，没有这个冲突；如果又误录了一条“张三也是部门”，这些声明就不能同时成立了。相应的推理工具可以帮助我们发现这种矛盾。

大家可以注意到，这里的推理和检查都有前提：含义必须先明确，相关知识也必须已经表达出来。工具检查的是这些知识之间的逻辑关系。至于李敏在现实中是不是经理，仍然要回到可靠的业务来源核实。

屏幕上的按钮是这两个例子的教学演示。今天介绍的是一般的形式推理能力，OntoWeave 当前还没有提供这里展示的 OWL 自动推理。

接下来，我们把目光从逻辑声明移到知识的组织方式，看看本体与知识图谱怎样联系起来。

## P09 本体与知识图谱：语义模型怎样支撑知识网络

我们用同一个例子，把本体和知识图谱的关系讲清楚。先看“员工”“部门”“所属部门”这几个词。本体要明确，员工是什么，部门是什么，以及“所属部门”这条关系表示员工归属哪个部门。这些定义提供了一套共同的业务含义。

再看具体知识：张三是一个员工，研发部是一个部门，张三的所属部门是研发部。我们把这些对象和关系连接起来，就得到了一小块知识图谱。这里用到的“员工”和“所属部门”，都引用了刚才明确的定义。

请看右边这张图。上面是本体提供的定义，下面是具体对象和事实。两条向上的虚线告诉我们，张三属于员工这一类，研发部属于部门这一类；上下两处“所属部门”也使用同一个含义。这样，定义和事实就关联起来了。

整张图展示的是一种采用本体的知识图谱。我们可以说，本体在其中承担语义模型的角色，帮助大家一致地理解和使用知识；图谱则把定义、对象和事实组织成可以关联和查询的网络。本体还可以被其他系统引用，同一套定义也可以被多个图谱复用。

因此，我们不能简单地把“上面全是本体、下面才叫知识图谱”作为两个概念的严格边界。知识图谱可以包含本体定义，本体本身也可以包含具体个体。这张图的重点，是让大家看到本体怎样为知识图谱提供含义。

理解了这个关系，我们再把本体放到 AI 的发展路线中，看看这种明确表达知识的方法，怎样与大模型的学习能力配合。

## P10 AI 的两条路线：符号主义与联结主义

我们可以先从两种不同的思路理解 AI。

符号主义侧重把知识明确地表示出来。一个符号代表什么，一个概念和另一个概念有什么关系，什么条件下可以得到什么结论，都尽可能写清楚，然后由程序进行查询、匹配或者推理。前面讲的本体，就属于这条知识表示路线。专家系统是这条路线早期的重要成果，下一页我们会具体看。

联结主义则侧重通过相互连接的计算单元来学习。神经网络是它的核心代表。训练过程中，系统不断调整连接权重等参数，从数据和反馈中学会识别模式、预测或者生成内容。沿着这条路线，发展出了深度学习，也支撑了今天的大语言模型。

比如“这单找谁批”和“应该交给哪位领导”，说法不同，语言模型可以理解它们可能在表达相近的意图。而本体可以明确，这个业务里的“部门负责人”究竟指哪一种关系。

这两条路线长期并行发展。把它们放在一起看，我们就更容易理解，为什么语言模型的学习能力与明确的业务知识可以互相补充。先从符号主义的一个典型应用——专家系统——说起。

## P11 专家系统：把领域经验写成可用的规则

专家系统的基本思路，是把某个专业领域里的知识整理到知识库中，再让推理机制结合当前事实，给出判断或建议。

一个经典例子是二十世纪七十年代的 MYCIN 研究系统，它利用医学知识和规则，研究感染诊断与治疗建议。今天我们只借这个历史例子理解系统结构。

回到差旅场景，我们可以把专家系统分成三个部分看。第一部分是知识库，保存概念、事实和规则。比如，如果申请适用这条政策，申请人属于某个部门，而这个部门的当前负责人是某个人，那么就由这个人审批。

第二部分是推理机制。它选择有关规则，把查到的事实代入条件，条件满足时产生结论。如果缺少必要事实，也可以继续提问或查询。

第三部分是结论和解释。系统除了给出审批人，还可以说明用了哪条规则、依据哪些事实、经过了什么判断。

这里也就能看出本体的位置：本体帮助明确概念和关系的含义；专家系统则在领域知识之上，增加了求解和交互机制。一个是知识模型，一个是利用知识完成任务的应用系统。

这种方式在边界明确的专业任务里很有价值，但专家经验的获取、例外的处理和规则维护，也需要持续投入。下面我们把这两条 AI 路线放在一起比较。

## P12 两条路线，各有擅长与代价

如果用一句话概括，符号主义的长处在于明确，联结主义的长处在于学习复杂模式。

明确知识有什么好处？我们可以逐条审阅定义和条件，检查一条规则为什么成立，也可以在业务变化时，定位需要修改的地方。代价是，这些知识需要有人整理和维护；遇到没有覆盖的情况、大量例外或者很模糊的输入，处理起来会比较费力。

神经网络则可以从数据里学习许多很难逐条编写的模式。语言、图像和多样化表达，都是它能够发挥作用的地方。但学习依赖数据、训练和计算；一个结果究竟依据了哪些内部知识，往往难以逐项追溯，输出也可能不可靠。

回到我们的案例：用户怎样描述问题，可以有很多种说法；公司当前采用哪条审批政策，却需要有明确依据。前一部分适合发挥语言模型的理解能力，后一部分适合使用经过确认的知识和相应的检查机制。

这些是典型侧重，实际能力会有重叠。我们真正关心的是，怎样把它们组合起来，让各自擅长的部分服务于同一个业务任务。

## P13 Agent 怎样结合两条 AI 路线

大家看这张图，中间是 Agent，它围绕用户的问题组织信息和能力。

语言模型首先帮助理解用户想做什么，判断还需要哪些信息，并组织后续处理。资料检索帮助找到制度原文和上下文；本体提供明确的概念定义、关系和业务约定；业务系统提供当前事实；工具负责具体的查询、计算和获准操作。

例如，“部门负责人”是什么意思，可以从明确的业务语义中取得；这个部门今天由谁负责，要查询当前组织信息；如果需要真正提交审批，还要调用具备相应权限的业务接口。

需要严格执行的规则，可以交给相应的规则程序或业务程序，执行后把结果交回 Agent。这样，每一个判断就能找到它所依赖的知识或者执行结果。

这是一种容易理解的组合方式：用语言模型处理多样表达，用显式知识提供共同口径，再通过工具连接现实业务。它与神经符号结合的思路是相通的。实际效果仍然取决于知识是否正确，以及 Agent 是否正确使用了它。

下面，我们就用这套分工，把开头那张申请完整走一遍。

## P14 Agent 如何找到审批人

现在用户问：“T-101 应该找谁审批？”Agent 可以按四步完成这件事。

第一步，确认口径。先识别这是什么类型的申请，适用哪一条政策。在我们的设定里，政策指定的是申请人当前所属部门的负责人。

第二步，查询事实。差旅系统告诉我们，申请人是张三；人事系统告诉我们，张三属于研发部，研发部当前负责人是李敏。屏幕上的这条路径，就是把这些信息连接起来的结果。

第三步，核对条件。关系是否齐全？查询的时间口径是否符合政策？有没有把直属主管当成部门负责人？这些地方核对清楚，答案才有依据。

第四步，形成回答：“应由李敏审批，依据是本例差旅政策和当前组织查询结果。”如果还要提交申请，就继续走获准的业务操作，并核对执行结果。

我们再看一个信息不完整的情况：如果能确认张三属于研发部，但查不到研发部当前负责人，回答就应该停在这里，明确缺少哪项信息，再继续查询或询问。

这个过程里，语义决定应该沿着什么关系找，当前事实决定最终找到谁。掌握这套关系之后，它还可能被其他任务复用。

## P15 何时值得建本体？看跨任务的语义复用

到这里，我们可以进一步考虑投入是否值得。

如果只是偶尔查一条制度，已有的文档检索就能稳定回答，那么我们可以先使用这个轻量方案。本体的价值更容易在长期、反复的使用中体现出来。

看这三个助手。差旅助手需要确定审批人，报表助手需要按部门统计申请，组织助手需要查询部门负责人。它们任务不同，但都要理解员工、部门和负责人这些概念。

如果这套含义经过一次共同澄清，三个助手就可以引用同一份定义和来源说明。以后遇到术语歧义，也有一个共同的讨论基础。当然，各自的任务条件仍然要确认，比如报表统计的是申请提交时的部门，还是查询时的部门。

这种复用有收益，也有建设成本：澄清含义、连接来源、验证效果，都需要时间，后续还有维护工作。所以，比较适合先尝试的，是歧义多、关系多、经常重复使用，而且有人负责维护的业务范围。

选定这样的范围后，接下来就可以开始建立第一个有用的本体。

## P16 一个有用的本体怎样建立

建设可以从五件事开始。

首先，确定要解决的问题和范围。比如，我们先处理某一类差旅申请的审批人查询，把它涉及的政策和系统范围划清楚。

第二，澄清容易产生歧义的含义。“负责人”是哪一种负责人？“当前”按什么时间理解？如果资料里说法不一致，就把问题提出来，请业务人员确认。

第三，把确认过的含义建立成模型，明确概念、关系和业务约定。第四，连接事实来源，说明申请信息从哪里取，组织关系由哪个系统提供，模型中的业务含义怎样对应到实际数据。

第五，回到最初的问题验证。事实齐全时，能否找到正确的人并解释依据？负责人未知时，能否明确指出缺失？如果回答不对，我们再检查是定义、关系、来源还是使用过程出了问题。

Agent 可以协助阅读资料、提出候选概念、发现不一致，也可以调用平台保存和读取模型。业务人员则提供和确认业务含义，特别是资料中没有说清楚的部分。无法确认的内容，应该明确保留为未知。

这五件事可以来回迭代。随着模型持续建设，我们也需要一个地方来组织、维护和提供这些知识，这就引出了 OntoWeave。

## P17 OntoWeave：建模与业务使用如何连接

OntoWeave 的中文名叫“织义”。我们先用这张图看看，它怎样把业务知识的建设和使用连接起来。

从左边看，业务人员提供资料和任务，确认业务口径，也回答资料中没有说清楚的问题。图中间这个深绿色模块，是我们希望重点介绍的平台特性：建模 Agent。

建模 Agent 有自己的任务。它阅读业务资料，发现含义不清楚的地方，提出需要澄清的问题，再把已经确认的知识组织成概念、关系和业务约定。获得相应授权后，它可以提交模型变更，读取已建模型进行自查，并根据发现的问题继续修订。

它右边是语义知识与平台服务。这部分负责保存模型，对提交进行校验和应用，并按照权限和任务范围提供相关语义。建模 Agent 负责理解和组织业务含义，平台程序负责可靠地保存和提供这些内容，两者配合工作。

最右边则是业务 Agent。它使用模型中的定义、关系和条件，再结合外部业务系统里的当前数据完成任务。真正的数据查询和业务操作，仍由对应的系统和工具承担。

所以，这里有两类 Agent：建模 Agent 面向知识建设，业务 Agent 面向具体任务。我们把建模 Agent 单独列出来，就是因为它是 OntoWeave 支持业务语义建设的一项重要特性。下面再具体看看，这套平台提供哪些能力。

## P18 OntoWeave 提供哪些关键能力

从实际使用的角度，我们可以把 OntoWeave 的能力概括为四个方面。

第一，是 Agent 辅助建模。业务人员提供资料和需要解决的问题，建模 Agent 协助阅读、整理和发现缺口，把明确下来的含义组织成模型。在获准范围内，它还能提交修订并读取结果自查，让建模过程能够继续往前走。涉及业务口径的判断，仍然需要可靠资料和业务确认。

第二，是用多种视角观察同一份模型。对象、行为、规则、角色、流程，以及数据和接口映射，帮助我们检查不同方面的知识有没有关联起来。例如，一条审批政策涉及谁、使用什么关系、到哪里查询相关信息，都可以放到共同的模型里理解。

第三，是按任务获取语义。业务 Agent 提出问题后，平台根据获准范围提供相关定义、关系、条件和映射，让它能够取得完成当前任务所需的业务上下文，再去查询实际数据。

第四，是浏览和持续维护。我们可以在界面里查看模型中的节点与关系。发现遗漏或者业务发生变化后，继续澄清和修订，再通过业务问题核对结果。

拿差旅场景来说，输入可以是制度、访谈结果和系统说明；形成的成果是明确的概念、关系、政策和映射；交给业务 Agent 的，则是审批查询所需的相关语义。我们希望这些工作能够持续衔接，让一份知识被逐步完善、反复使用。下一页用实际界面来看这些模型怎样呈现。

## P19 在界面中查看 OntoWeave 的模型

大家现在看到的是 OntoWeave 的实际模型浏览界面。

我们先看搜索和筛选区域。可以按名称、资源标识，也就是 IRI，或者已经记录的业务说明寻找模型内容。下面这些节点和连线，则把知识对象以及它们之间的关联呈现出来。

界面上还有七类视角：对象、行为、规则、角色、流程、数据映射和接口映射。可以把它们理解为观察和检查业务知识的不同角度。比如看对象与关系，再看相关规则，或者看这些业务含义怎样连接到数据和接口。

截图里显示了已加载的节点数和已读取的关系数，这些数字反映的是当时的界面状态。实际使用时，更有意义的是围绕一个问题去看：有关的概念是否齐全，关系是否清楚，来源能否找到。

如果需要看细节，可以把图片放大。前面我们介绍了建模 Agent 和平台能力，这张界面展示了已经建好的模型怎样被查看和维护。大家可以从自己的一个具体业务问题开始，逐步确认相关概念、关系和条件。我的主要分享就到这里，谢谢大家，接下来可以结合常见问题继续交流。

## P20 FAQ：什么时候值得使用本体

“已经有 RAG，还需要本体吗？”

可以先看已有方案是否已经稳定解决问题。RAG 能把相关资料找出来，很多任务做到这一步就已经够用了。如果困难主要出现在跨对象的关系、不同材料中的口径冲突，或者多个助手反复理解同一套定义，那么可以试着补充显式语义建模，再用相同条件比较效果。

“直接把规则写进提示词，不也能做吗？”

可以，小范围任务往往就适合这样做。规则需要共享时，也可以先用统一文档、词典或者规则服务。只有当关联关系的表达和复用确实带来收益，值得承担建模与维护成本时，再进一步使用本体。

“本体会替代数据库或业务系统吗？”

业务记录和实际操作仍然由原系统管理。本体帮助明确数据代表什么、对象怎样关联、哪些条件适用，以及应该到哪里取数。比如负责人是谁，可以继续从人事系统查询；本体说明的是这个关系的含义和来源。

“所有业务都要先建本体吗？”

可以优先选择歧义多、跨系统关系多、同一套含义被反复使用的场景。简单、固定、一次性的任务，采用更轻的方案就可以。我们可以从一个有代表性的问题试起，用结果判断下一步投入。

“本体与知识图谱到底有什么区别？”

本体提供概念、关系及其语义约定，知识图谱用相互连接的对象和关系组织知识。本体可以作为图谱的语义模型。比如，本体明确员工、部门和所属部门的含义；图谱把张三属于员工、研发部属于部门，以及张三所属部门是研发部这些知识连接起来。这张图可以同时包含本体定义与具体事实。

## P21 FAQ：怎么建，哪些工作需要人参与

“必须先学会 RDF 和 OWL，才能参与本体建设吗？”

业务人员可以先从自己的专业知识出发，确认概念、口径、政策和例外。技术人员再根据用途选择合适的表达和查询方式。我们完全可以先把业务问题讲清楚，再讨论怎样编码。当前这个项目也没有把 OWL 自动推理作为使用前提。

“界面里的七个视角，是通用的本体方法论吗？”

这是 OntoWeave 当前组织和检查业务知识的方式，实际可以按场景取舍。它与前面介绍的类、属性、关系等组成关注点不同。七个视角并不要求建立七个本体，也不要求安排七个 Agent，其他平台可以采用不同方式。

“Agent 能全自动把模型建好吗？”

它可以承担不少工作，比如整理资料、提出模型、发现待澄清问题，以及调用平台保存和读取知识。但如果源材料本身没有说明负责人是谁，或者两个部门对同一个词理解不同，Agent 仍然需要可靠的信息和业务确认。最终是否可用，要通过独立验证来判断。

“是不是需要一次把整个企业建完？”

可以先完成一条范围明确、能够验证的业务链。把这条链里的定义、关系和来源确认好，再把已经稳定的公共知识用于相邻场景。这样，业务人员能较早看到结果，我们也能较早发现理解上的偏差。

## P22 FAQ：怎样保证质量并持续维护

“有了本体，就不会产生幻觉了吗？”

我们仍然需要检查整条使用过程。源材料可能有误，建模可能理解错，检索可能漏掉关键条件，Agent 也可能没有正确使用取得的知识。本体的作用，是让一部分含义和依据变得明确、可检查。对于缺失的信息，系统也应该能够合理地回答未知。

“业务规则变了，是否要全部重建？”

通常先看变化影响了哪些内容。比如，假设从二〇二六年十一月一日起提交的新申请改由直属主管审批，之前的申请仍按原政策解释。我们需要确认生效时间、适用范围，再修改相关语义和映射，并核对新旧申请的边界情况。同时，业务系统也要按确认后的政策执行，知识更新和实际执行需要对齐。

“怎样判断这套方案是否划算？”

比较时，尽量让两种方案使用同样的资料、业务澄清结果、模型、题目、数据和工具。然后看答案是否正确、条件是否完整、依据是否清楚，再分别记录建模、维护、人工确认和调用成本。这样才容易分清，收益来自本体本身，还是来自额外补充了更好的资料和工具。

“本体的权限，能同时保护数据库和业务操作吗？”

语义权限控制的是哪些业务知识可以被读取。数据库里的行列权限，以及审批、退款等操作权限，仍然要由相应的外部系统执行和验证。知道一项操作的含义，并不自动意味着有权执行它。

这些问题最终都要回到各自的业务。我们可以继续讨论：在大家的场景里，哪一个含义、哪一条关系，最值得先明确下来，让不同的人和 Agent 共同使用？
