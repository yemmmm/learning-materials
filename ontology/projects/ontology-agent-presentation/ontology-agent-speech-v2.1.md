## P01｜本体如何帮助 Agent 理解与处理业务

大家好，今天想和大家讨论一个很具体的问题：怎样让 Agent 在处理业务时，知道自己依据的是什么。

现在，我们已经能让 Agent 调用工具、查询数据库、检索文档，甚至发起业务操作。但在实际使用中，大家可能都遇到过一种情况：工具调用成功了，资料也找到了，最后的业务判断却不一定对。

我们今天就从一句很普通的客户提问开始：“这笔订单能退吗？如果能，为什么还不能马上退款？”

这句话背后涉及商品、订单、售后政策、时间计算、验收、审批和退款状态。我们会用它来理解，本体怎样把这些业务含义连接起来，以及 Agent 怎样使用这些依据。

后半部分会介绍我们的项目 OntoWeave，中文叫“织义”。电商案例中的商家、政策和订单都是虚构的教学材料，方便大家核对判断过程。

## P03｜Agent 的业务理解难题

先想象自己是客服。

客户问：“这笔订单能退吗？为什么还不能马上退款？”如果让 Agent 接手，它接下来应该查什么？

我们通常会想到订单状态、签收时间和售后政策，以及验收、审批和退款状态。但还有一个同样重要的问题：查到这些内容以后，它怎样知道每个条件的业务含义？

先把这个问题记住。我们从 Agent 完成任务的基本过程看起。

## P04｜Agent 怎样完成一个业务任务

用户的问题和首页相同：“这笔订单能退吗？为什么还不能马上退款？”假设当前会话已经选中了订单 A101。我们先看一条业务口径已经确认的完成路径，页面中的数据和接口结果都是虚构教学输入。

第一步，理解请求。语言模型把它拆成两个判断：能否申请退货，以及退款还缺哪些前提。订单号由当前会话提供，不靠猜测。

第二步，查业务事实。订单查询得到 A101 已签收、属于普通商品，签收时刻是十月一日上午十点。客户声明商品未使用。售后查询明确返回验收尚未开始、审批尚未申请；这里的“尚未”有状态支持。

第三步，查适用政策。找到本例的 RET-DEMO-v1：普通商品、客户声明未使用，申请时间从签收起算，间隔在零到 168 小时之间。退款还需要退回验收通过、客服批准。

第四步，计算并核对。拟申请时刻是十月六日上午十点，日期计算工具算出距签收 120 小时。时间条件满足，商品与声明条件也满足；验收与审批尚未完成，所以退款前提尚未满足。这里统一使用 2026 年、UTC 加八时区。

第五步，解释与继续。Agent 回答：按当前声明可以申请退货，但退款前还需完成验收并取得批准。本次只做教学判断，没有实际提交申请或发起退款；真正提交仍由业务系统重检条件、权限和重复操作。

这条路径依赖一个前提：政策口径、字段与状态的含义已经说清楚。下一页，我们暂时拿掉“七天从何时起算”的确认，看看第 4 步和最终答案会发生什么变化。

> 现场提示：每展示一个步骤，同时讲它在 A101 上做了什么、取得了什么。不要把教学输入说成真实接口调用结果。

## P05｜条件核对为什么会出错

上一页先看了业务口径已经确认的完成路径。现在保持同一订单的事实不变，暂时拿掉起算点的确认，只知道政策里写了“七天内”。

这笔模拟订单在九月二十八日上午十点付款，十月一日上午十点签收，客户打算在十月六日上午十点申请退货。这里所有时刻都在 2026 年，使用 UTC 加八时区；付款时刻只是为了比较解释而补充的输入。

如果把“七天内”理解为从付款起算，间隔是 192 小时，超过 168 小时。如果理解为从签收起算，间隔就是 120 小时，处于时间窗内。

订单事实相同，起算点的解释不同，条件核对和答案就会改变。本页是在展示缺少业务确认时的歧义，统一案例最终仍采用签收起算。

退款判断还有类似问题。“已签收”描述客户收到商品，不等于退回商品已经验收通过；“可申请退货”也不等于已经具备退款条件。商品范围、未使用声明、验收及审批状态，都需要明确含义。

因此，需要补足的依据既包括事实，也包括解释事实的业务含义和政策口径。接下来把常见方法放回前面的任务步骤，看看它们各自补足什么。

> 现场提示：先看付款起算的 192 小时，再切换签收起算的 120 小时。强调正在暂时拿掉起点确认，不是在更改案例政策。

## P06｜六种方法怎样补足判断依据

把这些方法放回刚才的退货与退款任务，它们的作用就会具体起来。

提示词和示例，对应理解请求与组织回答，可以要求 Agent 分开回答申请资格和退款前提。文档检索，也就是 RAG，对应查政策，找出 RET-DEMO-v1 的适用范围、时间窗和退款条件。

业务工具对应查事实与计算：取得 A101 的签收时刻、验收和审批状态，再由计算工具得到 120 小时。工具结果的业务含义仍要有依据。

专家澄清对应查政策和核对条件：资料只写“七天”时，要确认起点；状态编码没有说清时，要确认它表示尚未开始还是未知。

本体建模与复用，是把已经确认的定义、关系、条件及映射组织成知识模型，再让后续步骤和其他任务引用。例如，既能找到签收时刻对应哪个字段，也能从退款找到验收与审批前提。这里的方法是建立和使用本体，本体本身是形成的知识模型。

微调则发生在训练阶段，用售后问答样例改善拆题、回答和补问的任务适配。它不是每问一次订单就执行的步骤，也不能替代当前政策和实时事实的查询。

这些方法可以组合，RAG 可以检索本体，工具也可以执行已编码的规则。接下来继续看：这次问清楚的签收起点、验收含义和退款前提，怎样在不同任务中持续保持一致？

## P07｜不同方法的局限性

如果把退货规则分别写进客服、仓库和财务三个应用的提示词，就需要分别维护，时间久了容易出现不同口径。

通过 RAG 找到一段“七天内可退”的政策，也还要确认版本、适用商品和例外。微调形成的任务适配，难以充当一份随时更新、能够精确引用的政策库。工具返回一个状态编码，Agent 仍需要知道这个编码意味着什么。

专家可以解决歧义，但确认结果还需要沉淀。本体也有自己的成本：定义要建对，相关知识要读全，政策变化后要维护。

因此，走到这里，我们只是发现了“共同引用业务含义”的需求。统一文档、业务词典、共享配置和规则服务，都可能满足其中的一部分。

接下来要看的是，显式表达对象之间的关系，能否在跨环节、跨任务的使用中带来实际价值。

## P09｜Ontology 的思想来源与工程应用

先分清 Ontology 这个词在不同语境中的含义。

哲学关注存在、类别及其关系。知识工程借鉴这些思路，把一个有边界领域中的概念、含义和关系明确表达，形成可共同使用的模型。本次分享讨论的就是这种工程本体。

这里先介绍一下 Palantir。这是一家 2003 年成立的美国软件公司，最初服务美国情报机构，后来扩展到商业企业，主要帮助组织把分散的数据、分析和业务运营连接起来，并使用 AI。

它的主要平台包括 Gotham、Foundry、Apollo 和 AIP。可以先把 Gotham 理解为面向政府及情报等场景的分析平台，Foundry 负责业务数据与运营，Apollo 支持软件部署与持续交付，AIP 支持把大模型接入实际业务应用。我们今天主要关注 Foundry 中的 Ontology。

用两项有明确年份的成果建立印象。2017 年，空中客车与 Palantir 合作推出 Skywise 航空数据平台，把来自不同系统的航空数据连接起来，用于分析和运营。根据 Palantir 在 2026 年二月二日发布的业绩公告，它 2025 年全年营收约 44.75 亿美元，同比增长 56%。前者说明实际项目应用，后者说明公司整体业务规模，不代表这些收入都来自 Ontology。

之所以在这里介绍它，是因为 Foundry 把 Ontology 用于连接业务数据、对象和操作，Ontology MCP 又提供了向 Agent 暴露相关能力的一种接入方式。

Palantir 并非 ontology 的发明者，Foundry 的产品体系也不能直接等同于 OWL 本体或 OntoWeave。本体驱动 Agent 在这里指一种可选的架构思路，是否采用仍要结合业务判断。

明确这个语境后，下一页用订单、退货申请和退款单，具体解释工程本体定义中的对象、含义与关系。

## P10｜什么是本体（Ontology）

在工程里，我们可以把本体理解为：把一块业务中重要的对象、含义、关系及适用条件，整理成可共同使用、机器可处理的模型。

这里区分三个层次。本体是形成的知识模型；访谈、澄清、表达、验证和维护它，可以有相应的方法论；让多个 Agent 围绕同一套本体组织业务任务，是一种架构思路，宽泛地也可称为设计范式。建立和使用本体的方法，与本体这一产物分别理解。

比如，订单记录一次购买，退货申请记录客户提出退回某个订单项的请求，退款单记录退款请求及其处理状态。这三个对象分别有自己的含义，也存在明确关联。

专业一点的说法，是“显式的领域概念化表达”。“显式”表示含义和关系被写清楚；“领域”表示我们讨论的是一块有边界的业务；共同使用，则要求不同人和程序能够引用同一套身份和定义。

自然语言说明帮助理解，稳定的资源身份和结构化关系帮助精确定位与连接知识。

所以，建设本体需要落实这些表达。仅仅把一份制度文档换个名字，还没有完成这一步。

## P11｜用本体描述退货业务

现在看图中的关系。

客户下单，形成订单。一个订单包含订单项，订单项就是其中的一条商品明细，它关联具体商品。

退货申请针对订单项，退款处理又关联退货申请。上方的政策说明申请条件，也规定退款还需要满足哪些前提。

这样的关系可以帮助我们沿着问题找到相关知识。问某个订单项能否退货，就要找到它对应的商品和适用政策；问为什么还不能退款，就要继续查申请之后的处理条件。

这页先看骨架。后面会补上时间窗、声明口径、验收和审批要求。

还要区分概念和记录：“退货申请”是一类业务对象，“申请 R001”才是一次具体申请。具体订单和申请记录，仍然来自外部业务系统。

> 现场提示：先展示业务对象，再展示带动词的关系，最后显示政策条件。后面 P30 会回到同一骨架。

## P12｜本体中的基本表达

读这种模型时，可以先掌握几种基本表达。

“退货申请”是一类对象，这就是类。“申请 R001”是一个具体对象，这就是个体。申请时间对应一个日期时间值，这是属性。申请针对某个订单项，这是资源之间的关系。

分类层级又是另一种表达：“退货申请是售后申请的一类”。它和“申请针对订单项”描述的含义不同，所以图里使用了不同线型。

语义层里也可以有具体的知识个体。比如 RET-DEMO-v1 就是一份具体政策，我们可以稳定地引用它，以及它适用的对象和条件。这不要求把全部订单行搬到平台里。

实际建模时，还要保留条件、范围、例外和未知。某项含义没有确认，就把它标明，而不是根据名字相似或字段样例替业务做决定。

## P13｜本体、知识图谱与数据库的分工

这几个词经常一起出现，但它们关注的层面不同。

上方，本体约定“退货申请”“订单项”是什么意思，以及申请可以怎样关联订单项。

左下，知识图谱把具体知识按实体和关系连接起来。例如，RET-DEMO-v1 是一份退货政策，它适用于普通商品。沿着这些关系，可以取得相关定义和说明。

右下，数据库保存和查询具体业务记录。例如订单 A101 的签收时刻。订单发生变化，业务系统继续负责更新这些记录。

这些能力可以组合。知识图谱里也可以包含概念定义，图数据库可以保存知识图谱，关系型数据库的数据结构也可以表达字段与约束。

在 OntoWeave 这条方案中，业务行保留在外部系统，平台保存业务语义和映射，消费 Agent 再把它们连接起来使用。

## P14｜本体怎样帮助 Agent 工作

现在把 Agent 放回图的中央。

用户提出问题后，Agent 先按权限取得相关定义、对象关系、适用政策、条件说明和数据映射。这些内容合起来，就是这里说的“语义上下文”。

有了这些依据，它才知道应该查询哪些业务事实，字段和状态怎样解释，以及还缺什么信息。随后，它调用数据库或 API，取得实时事实，进行必要计算，再组织回答。

原始资料也仍然有用，需要时可以通过 RAG 补充说明。问答、分析和操作建议，可以复用同一份业务语义。

这个过程里，本体提供依据，Agent 组织任务和解释结果，外部系统提供事实并执行操作。即使 Agent 知道了退款前提，也还需要取得业务系统授予的操作权限。

## P15｜业务含义怎样表达与查询

再往技术层看，可以把 RDF 理解为一种图数据模型。它用主体、谓词和客体组成一条陈述。

图中的例子是：“RET-DEMO-v1，适用于，普通商品。”政策和商品是两端的资源，“适用于”表达关系。多条陈述引用相同资源，就能连接成图。IRI 为这些资源提供可稳定引用的身份。

RDFS 提供基础类型与层级词汇，例如属于某个类、某个类是另一个类的子类。OWL 可以表达更丰富的形式语义。SPARQL 则用于查询 RDF 图中的资源、关系和值。

可以把它们先记成几个职责：表达陈述、描述类型层级、表达更丰富的形式语义，以及查询图。

还有一个边界要记住：业务条件能够以说明形式被机器读到，并不意味着这些条件都已经被编译成可执行程序。时间比较和实际业务操作，还要由相应能力完成。

## P16｜形式推理的作用与边界

这页用一个简单例子解释形式推理。

已知退货申请是售后申请的一类，售后申请又是业务申请的一类，那么可以推出：退货申请也是业务申请的一类。这里的分类传递，可以由 RDFS 支持，OWL 还能够表达更丰富的公理。

这类推导依靠明确前提和形式语义。但判断 A101 能否退款，还需要具体时间、商品类别、客户声明、验收和审批事实。分类关系本身并没有提供这些答案。

同时，没有记录一项事实，也不能自动解释为这项事实是假的。没有读到“审批通过”，可能是尚未审批、事实缺失、读取不完整，或者没有权限，需要分别判断。

这里讲的是技术原理。演示所依据的项目范围中，OntoWeave 当前不提供自动推理运行，也没有在这页展示真实推理回执。

> 现场提示：先展示两条已有分类关系，再展示右侧独立的推导线。强调“能推出分类关系”和“能判断某笔退款”所需的前提不同。

## P17｜本体的优势与适用条件

回到客服、仓库和财务。

客服关心能否申请退货，仓库关心商品怎样验收，财务关心退款还缺哪些前提。它们面对的是不同任务，但需要共同理解政策、订单项、验收和审批。

显式关系的价值，可以出现在这种跨环节问题中：从退款沿关系找到相关申请，再找到验收、审批和适用条件。数据映射帮助定位相应事实，未知说明限制答案的范围。

如果只是一个固定任务，几条配置或者一份统一文档可能已经足够。只有当这些跨对象、跨任务、跨系统的关系需要持续复用，且实际收益值得维护投入时，进一步建模才有意义。

因此，比较稳妥的做法是选一个有代表性的问题，比较正确性、人工确认和维护成本，再决定是否扩展。

## P18｜OntoWeave 与建模方法

前面解释了本体可以怎样帮助 Agent。

接下来介绍我们正在建设的 OntoWeave，以及怎样把业务材料逐步变成可用的语义模型。

这里有两项工作需要配合：平台提供保存、检查和读取能力；业务人员与 Agent 形成准确的业务表达，并通过实际消费来验证它。

## P19｜OntoWeave 的定位与责任边界

图上几类参与者，各自承担一部分责任。

业务人员确认业务含义、适用范围和歧义。建模 Agent 读取获准资料，整理概念、条件、关系与映射。

OntoWeave 保存这些语义，管理写入和访问。消费 Agent 再按权限读取已建知识，查询业务事实，处理用户任务。

外部数据库和业务 API 则继续负责业务记录、数据访问与实际操作。

平台可以检查字段是否符合合同、引用是否有效、写入是否完整，但“七天从哪里起算”仍然要有业务依据。业务角色知识和应用访问权限，也需要分别表达与验证。

明确这些分工，才能在出现错误时，判断应该补业务资料、修模型、补读取，还是处理外部系统的问题。

## P20｜系统架构

从技术组件看，上层是管理界面、建模 Team 和消费 Agent。管理界面通过应用接口接入，Agent 通过工具接口接入，两类入口复用下面的应用服务。

服务层处理身份与范围授权、写入校验和应用，以及语义查询与读取。存储层也有分工：PostgreSQL 保存平台元数据与工作状态，RDF 和 Oxigraph 保存业务语义图。

右侧的业务数据库和业务 API 在平台之外。消费 Agent 取得语义依据之后，还要通过相应系统的授权，查询订单或发起业务操作。

图里保留了演示制作时的 dry-run 和 apply 标签。最近一轮已确认设计，正在把模型批次写入简化为：建模 Agent 直接提交已确定的语义变更，程序完成转换，在一次应用内校验并原子写入。独立的 dry-run 和 Protocol 翻译审批，不再作为这条写入路径的必经环节。

这个设计把技术转换交给程序，业务含义仍需有来源并接受验证。相关工程实现与验证正在进行，不能据此宣称真实业务质量已经通过。

> 现场提示：图的分层和存储分工可以直接讲。写入路径按钮及其 dry-run 标签属于旧图示，用上述口头补充解释即可；不要把新设计讲成已经完成真实验收的上线成果。读取路径可正常高亮。

## P21｜建模方法论：先完成一条可验证的业务链

开始建模时，可以先提出一个具体的业务问题：“能申请退货，是否就能退款？”

我们把这类模型应当支持回答的问题，叫作能力问题，也就是 CQ。它帮助确定要表达哪些知识，以及最后怎样判断模型是否有用。

然后按照业务目标、生命周期和依赖，拆成可分步分析、验证的逻辑切片。先完成一条最小完整链，实际读出来、回答一次，再扩展相邻范围。

在这个过程中，共享术语、跨切片依赖、映射和跨切片问题，要保留项目级视图。否则每个局部都像是对的，放在一起却可能对不上。

切片是一种工作组织方式，不按数据库有几张表直接决定建几个本体，也不默认一个切片配一个 Agent。我们先把当前范围内重要的条件、例外和未知处理完整。

## P22｜七个视角检查同一业务模型

七个视角，是检查这条业务链有没有遗漏的方法。

对象视角看订单、订单项、商品和申请分别是什么。行为视角看提交、审核和退款等动作。规则视角看时间窗、适用范围和动作前提。

角色视角看客户、客服和仓库怎样参与。流程视角看申请、退回、验收和退款各阶段怎样衔接。

数据映射视角，要回答业务含义对应哪个字段。例如签收时刻来自 `orders.signed_at`。接口映射视角，要回答由哪个外部能力查询状态、提交申请或执行退款。

这些视角都围绕同一段业务。每个视角都要说明：已经确认了什么，还缺什么，哪些在当前范围不适用。规则视角需要把条件说清楚，并不要求为每个条件生成规则脚本。

> 现场提示：不用连续点击七次。先停在“对象”，再切到“规则”和“数据映射”，让听众看到同一张图被从不同角度检查。

## P23｜Agent Team 的自动建模方式

这些工作可以由 Agent 协作完成，但仍要明确职责。

建模成员负责读资料、澄清歧义和提出业务表达。协调成员负责切片、共享定义和反馈的衔接。出题工作帮助形成能力问题，交付监督负责授权、进度和交接。

图中还有一个写入成员 Protocol，这是演示制作时的职责配置。按照刚才介绍的新设计，Modeling 将直接提交语义变更，技术转换和执行字段交给程序处理，不再依赖 Protocol 翻译审批的往返。

这些安排可以按实际依赖调整，不需要为凑固定角色数量而增加 Agent。

图下方是另一条重要的工作线：独立消费和独立判定。验收者读取已经写入的模型，回答业务问题，再核对依据；它不能一边验收一边修改被验收模型。

生产过程可以依据公开反馈修订，隐藏验收内容则保持隔离。这样，我们才有机会分清模型真正可用，还是生产者熟悉自己刚写下的答案。

> 现场提示：重点指向上、下两条职责线。上方 Protocol 标签按旧图解释，新路径按本页正文补充。不要将职责图讲成固定人数或固定顺序的流程要求。

## P24｜消费 Agent 实际需要读到什么

“读到了语义上下文”具体意味着什么？看右侧这张政策卡。

首先，它要知道自己找到的是哪一份政策，以及政策与哪些对象关联。其次，要读到决定答案的条件：普通商品、客户声明未使用，以及从签收到提交申请的间隔在零到 168 小时之间。

继续问退款时，还要读到验收通过、客服批准这些前提。数据映射则告诉它，签收时间、商品类别和售后状态分别从哪里取得。

最后，还要检查读取范围和状态。如果分页没结束，或者结果被截断，就可能还需要补读。读到几个相关节点，并不能说明判断所需内容已经齐全。

这里展示的是虚构内容的人可读示意，不是真实接口响应。受治理读取，指按权限读取，并说明本次读取的限制；它本身不会保证整个知识库完整，也不会保证 Agent 的业务答案正确。

## P27｜模拟业务背景与输入材料

先把业务范围限制清楚：这里只讨论单件商品整件退货，以及商品款整额退款。运费、促销分摊、部分退货和跨境问题，都不进入这个教学范围。

输入材料有售后政策与业务确认、术语说明、数据库字段和编码说明、售后接口合同，以及客户这一次的声明。

三个订单用于对照。A101 在十月一日上午十点签收；A102 在九月二十七日上午十点签收；A103 的签收时间缺失。三者都是普通商品，客户都声明未使用。

## P28｜建模前的业务确认

接下来，模拟商家回答了几个决定结果的问题。

“七天内”，具体指从签收时刻到提交申请时刻的连续时间差，范围是零到 168 小时，包含两端。申请时先采用客户的未使用声明，实际商品状态要由后续仓库验收确认。

政策适用于普通商品，定制商品不在这份政策范围内。能申请退货，也不表示可以立即退款；退款还需要退回验收通过和客服批准。

如果缺少必要信息，答案应当保留未知，并指出需要补充什么。

这里也能看到业务确认和数据结构的区别。数据库里出现一个 `created_at` 字段，不足以说明它就是签收时间。字段含义与编码含义，需要由资料和业务确认支撑。

实际提交时，业务系统还要使用真正的提交时刻重新检查条件。

## P29｜业务切片与共享定义

确认口径以后，可以把工作组织成三个逻辑切片。

第一段是退货资格，回答是否允许提出申请，处理商品、声明和时间窗。第二段是退货处理，表达申请、退回和验收阶段。第三段是退款处理，表达审批、退款前提和对应接口。

三段共同引用客户、订单项、商品、政策和状态含义。它们有前后依赖，也需要共同回答跨环节问题。

比如，即使先只完成退货资格这条链，也要保留“可以申请与退款完成是不同阶段”的含义。否则，局部答案很容易被消费者理解过头。

这三个切片帮助我们分步完成工作，并不预先规定三套本体或三套互不相干的知识。

## P30｜退货与退款的语义模型

我们再回到前面那张关系骨架，现在把确认后的内容补上。

政策 RET-DEMO-v1 规定普通商品的申请条件：客户声明未使用，提交时刻减签收时刻的间隔，在零到 168 小时之间。

退款处理关联相应退货申请，还需要知道验收是否通过、客服是否批准。真正执行时，业务系统仍要检查权限和防重复。

这些条件、范围、例外与未知，以业务说明和相关关系组织起来。数据映射和接口映射，则指向取得事实、执行动作所需的外部能力。

这张图在表达判断依据。A101 的签收时间是多少、仓库有没有验收，还要从下一步的业务输入取得，不能从模型图本身推出来。

## P31｜语义怎样连接 SQL 与 API

现在看具体事实从哪里来。

签收时刻映射到 `orders.signed_at`，商品类别映射到 `products.category`。订单项通过订单编号和商品编号，连接到对应订单与商品。Agent 应当先取得获准语义，再结合真实数据结构生成查询，避免只凭表名猜连接和口径。

客户是否声明未使用，来自客户本次输入。验收、审批和退款状态，则来自模拟的外部售后查询接口。时间差由日期时间计算工具给出。

动作也分别映射：提交退货申请和执行退款，是不同业务接口，不能因为前一步成立就当作后一步成功。

例如在本例接口合同里，ACCEPTED 只表示退款请求已受理，SUCCEEDED 才表示外部系统确认完成。仅凭 HTTP 请求成功，或者接口名字叫“退款”，都不能推出钱已经退回。

这里的 SQL 和 API 都是教学设计，本次没有接入或调用真实售后与支付系统。

## P32｜案例一：能申请，为什么不能马上退款

现在完整回答 A101。

先读政策：普通商品、客户声明未使用，且提交与签收之间的间隔在零到 168 小时以内。

再看事实：订单在十月一日上午十点签收，拟申请时刻是十月六日上午十点。计算工具给出的间隔是 120 小时，满足时间条件。商品是普通商品，客户声明未使用，因此按当前输入，可以申请退货。

接着看退款条件。模拟售后接口明确返回：验收尚未开始，客服审批尚未申请，没有已有或进行中的退款。这些状态说明，验收和审批前提还没有完成。

因此，给客户的回答可以是：“按当前政策和您的未使用声明，可以申请退货，实际商品状态仍待验收。当前尚未验收，也尚未获客服批准，所以不能立即退款。”

大家留意，每个结论都有自己的依据。政策来自语义模型，时间和类别来自业务系统，声明来自客户，时间差来自计算工具。Agent 把这些结果组织成了业务解释。

这里没有实际提交申请或执行退款。若客户决定申请，业务系统还要在真正提交时重新检查。

> 现场提示：先展示政策与事实，再显示右侧业务回答。可以在展示回答前，请听众判断“现在能否直接退款”。“尚未验收、尚未审批”由明确状态支持，不能换成从空结果推断。

## P33｜案例二：超时与信息不足

相同政策再看另外两笔订单。

A102 从九月二十七日上午十点，到十月六日上午十点，间隔是 216 小时，超过 168 小时。这里有明确事实支持，可以说明它不符合本例政策的时间条件。

A103 则缺少签收时刻，无法计算间隔。它需要的回答是：“暂时无法判定时间条件，请补充签收时刻。”

这两个结果要分开。一个条件已经明确不满足，可以解释不满足的原因；必要条件还无法确定时，就保留相应未知。

同样，接口读取失败、权限不足和业务字段缺失，也应当各自说明。没有读到某项内容，不能统一说成“这项事实不存在”。

如果 Agent 能准确指出缺什么，并提出合适的补问，这本身就是一个正确的业务结果。

## P34｜怎样验证建模效果

到这里，教学例子已经可以手工核对。但要证明模型在实际系统里可用，还需要独立验证。

可以沿着四个环节检查：资料依据是否明确；模型是否忠实表达了概念、关系、条件和未知；实际检索是否取得了必需内容；消费 Agent 是否正确使用这些依据回答。

正式验证时，应当在真实授权接口读取，由独立消费 Agent 作答，再独立核对。除了正常情况，还要检查边界、未知、跨切片和权限问题。

比如恰好 168 小时应当包含在内，加一秒又怎样；缺少声明、缺少审批状态、已经受理的退款与已经完成的退款，答案都要有所区别。

如果要与文档 RAG 比较，两边必须共用相同资料、业务澄清、政策版本、数据快照、题目、工具和权限，并尽量固定语言模型与调用条件。否则，只给本体方案补全业务规则，再把收益都归因于本体，比较就失去了依据。

建模、维护、人工确认和运行成本也要分别记录。今天这份案例提供的是验证设计和教学预期，没有新增真实效果成绩或提升百分比。

现在可以回扣开场：A101 按声明可以申请，依据是适用政策、商品类别和 120 小时间隔；不能立即退款，依据是尚未完成的验收和审批。每一步，都需要相应的知识或事实支持。

## P35｜FAQ：什么时候值得使用本体

最后，用几组常见问题帮助大家判断怎样落地。

**第一个问题：已经有 RAG，还需要本体吗？**

如果现有文档检索已经能稳定回答问题，可以继续使用。跨对象、跨任务的关系需要明确复用时，再尝试把本体作为结构化知识来源，并通过同条件对照判断收益。两种方法可以配合。

**第二个问题：直接把规则写进提示词不行吗？**

小范围任务可以。统一文档、业务词典或规则服务，也都能维护共同口径。是否进一步建模，要看显式关联带来的复用和维护收益，是否值得投入。

**第三个问题：本体会替代数据库和业务系统吗？**

在今天讨论的方案里，业务记录和操作继续留在原系统。本体描述它们的含义、关系、条件和映射，帮助 Agent 正确使用这些系统。

**第四个问题：所有业务都要先建本体吗？**

可以优先找含义歧义多、跨系统关系多、同一定义被反复使用的场景。简单固定的任务，先采用能满足需求的轻量方案。

> 现场提示：如果进入自由问答，可以按现场提问选择展开，不必逐字读出四个问题。需要回看时，使用本页到 P07、P13、P17 的链接。

## P36｜FAQ：怎么建，哪些工作需要人参与

**必须先学会 RDF 和 OWL 吗？**

业务人员首先要确认概念、条件和口径。技术人员再选择合适的表达与查询方式。理解本体，不要求每位业务人员先写 OWL，当前项目也不要求启用自动推理。

**七个视角，是不是七个本体或七个 Agent？**

它们是检查同一业务的不同角度。切片怎样组织、知识怎样存储、人员怎样分工，都应当按真实依赖安排。

**Agent 能全自动把模型建好吗？**

资料整理、提出表达、调用平台和部分检查，可以自动完成。但资料缺失、口径冲突、范围和授权问题，需要相应负责人确认。最终质量还要靠独立验证。

**是不是要先建完整个企业，才有价值？**

可以先完成一条有代表性、可读取、可验证的业务链。例如先把“是否可以申请退货”讲清楚，再逐步扩展到验收和退款，同时维护共享定义。

这样的推进方式，也能更早发现资料、模型或消费过程中的真实问题。

## P37｜FAQ：怎样保证质量并持续维护

**有了本体，就不会产生幻觉了吗？**

仍然可能出错。源材料可能有问题，模型可能表达不准，检索可能不充分，Agent 也可能用错依据。所以需要逐环节验证，并允许在信息不足时回答未知。

**业务规则变了，是不是要全部重建？**

先确认变更的业务含义、生效时刻和适用范围，再沿实际依赖修订相关定义、条件和映射。

右侧是一个独立的教学变更：假设 A 店把时间窗从 168 小时改为 240 小时，并规定从 2026 年十一月一日零点、UTC 加八时区起提交的申请采用 v2，此前提交的仍按 v1。决定采用哪个版本的依据，是提交时刻。

这时，业务负责人确认口径，维护者和建模 Agent 修订语义，外部系统负责人对齐实际执行，独立验证再检查新旧适用范围及边界。语义更新本身不会自动更新退款系统。这也不表示平台已经具备自动影响分析或任意历史版本读取能力。

**怎样评估成本与收益？**

在相同资料、澄清和工具条件下，比较正确性与完整性，同时记录建模、维护、人工确认和调用成本。维护是否更省，要从实际工作中得出结论。

**本体的权限，能保护外部数据库和退款操作吗？**

语义权限控制语义知识的读取。外部数据库的行列访问，以及退款操作权限，仍由对应业务系统负责，需要分别验证。

最后，再回到开场那句提问：“这笔订单能退吗？为什么还不能马上退款？”要给出可靠回答，需要准确的业务定义、足够的具体事实、适当的工具，以及能够核对的验证。

大家可以从自己的业务里找一个类似问题：同一个词，是否在几个系统里有不同解释？一次操作，是否依赖多个环节的条件？如果把这些含义和关联明确表达出来，能帮助哪些任务？

今天就分享到这里。谢谢大家，接下来欢迎结合自己的业务一起讨论。
