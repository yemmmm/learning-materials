# 本体与 Agent：v3.0 讲者备注

## P01 本体与 Agent

我们从一件很普通的事情开始：张三提交了一张差旅申请，希望 Agent 帮忙找到审批人。沿着这个问题，我们会认识本体是什么，区分本体与 RDF、OWL 等表达技术，再看 Agent 如何使用领域知识，最后介绍 OntoWeave。这里的组织、人员关系与政策均为教学设定。

## P02 张三的差旅申请，该由谁审批？

政策指定的是申请人当前所属部门的负责人。张三属于研发部，研发部负责人是李敏，因此本例应由李敏审批。王强是张三的直属主管，这是另一种关系。我们刚才把政策中的概念和关系，对应到了具体对象上。这个任务不要求证明语言模型一定会答错，而是帮助我们看清回答所依赖的业务含义。这些含义可以怎样明确记录，并被重复使用？

## P03 本体：对领域语义的明确建模

知识工程中的本体，可以先理解为一份明确的领域语义模型。它说明业务里有哪些概念，这些概念是什么意思，对象怎样关联，以及哪些语义约定成立。例如，申请人与部门如何关联，经理和员工是什么分类关系。我们选择当前问题需要表达的知识，不需要把整个世界一次描述完整。接下来把现实中的业务、语义模型以及表达技术分开看。

## P04 现实世界、本体、形式表达

左边是现实业务：张三在一个部门工作，提交了一张申请。中间是我们对这些事情的理解：员工、部门、申请各是什么，它们如何关联。右边是用什么方式把含义记录下来。实际保存的本体产物当然有表达形式，但我们可以把语义选择和技术选择分别讨论。同一套业务理解可以通过不同方式表达。下面先认识本体的常见组成。

## P05 本体的常见组成

先看空心的概念：经理、员工和部门是类。姓名和入职时间描述对象的特征。隶属于说明两个对象之间的联系。经理是一类员工，是有逻辑含义的分类断言。底部实心的张三和研发部是具体对象。这里按教学目的把属性和关系分别列出，在 OWL 中，对象间的关系通常也属于属性。公理用于陈述知识，不是额外的一种业务对象。各项按用途选择，个体可以按需纳入。

## P06 “员工”与“张三”处在不同层次

员工是一种概念，张三是具体对象。部门是一种概念，研发部是具体对象。上面的定义告诉我们如何理解所属部门关系，下面的事实告诉我们这次关系连接着谁。即使负责人发生变化，上面的词汇与关系定义仍然可以继续使用。具体事实可以保存在知识系统中，也可以留在人事和差旅系统中，在使用时读取。这是定义与事实的作用区别，不是规定本体只能有类、知识图谱只能有实例。

## P07 RDF 与 OWL 分别做什么

RDF 用主体、谓词、对象这样的三元组来陈述知识，多个陈述通过共同对象连接成图。OWL 为本体表达提供形式定义的含义，可以描述类之间的互斥等关系。两者可以一起使用，也不是互斥的文件格式。RDF 既可用于事实，也可用于定义；RDFS 已提供一些基础分类词汇。我们先把这两个技术名词放在表达层，接着看看明确的逻辑含义能够带来什么。

## P08 形式语义怎样支持推理与检查

经理属于员工，李敏属于经理，因此可以推出李敏也属于员工。这里是给定知识下的逻辑后果。右边是另外一个假设误录的例子：如果员工与部门已经声明为互斥，却把张三同时归到两个类别，就会产生矛盾。能够做什么检查和推导，取决于表达范围与所使用的推理工具。逻辑一致不自动证明外部数据真实，形式推理也与语言模型组织业务判断的过程有所不同。OntoWeave 当前不提供这里展示的 OWL 自动推理运行。

## P09 本体与知识图谱怎样配合

本体强调概念与关系的明确含义。知识图谱强调把有关对象的知识组织、连接起来，供查询和使用。一个知识图谱可以同时包含定义和具体事实，它也可以采用不同的图技术。RDF 和 OWL 则属于相关的表达技术。这里用同一幅图展示协作方式，避免把本体、知识图谱和某一种格式混为一谈。接下来，把这些知识放到 Agent 的工作过程中。

## P10 本体在 Agent 体系中的位置

Agent 使用语言模型理解问题、组织计划和解释结果。语义模型提供组织特定的概念、关系和政策含义。业务系统提供当下的申请人与组织关系，工具则承担查询、计算或执行操作。这是一种概念分工，实际系统可以有不同实现。Agent 读取本体，不表示本体直接修改了语言模型参数。我们把这些分工放回刚才的审批任务，完整走一遍。

## P11 Agent 如何找到审批人

第一步，取得适用政策以及申请人、所属部门、负责人这些定义。第二步，从差旅系统取得申请人张三，从人事系统取得研发部与李敏的事实。第三步，结合政策选用所属部门负责人这条路径。第四步，明确回答李敏，并解释每一个依据。直属主管王强对应另一种关系。若负责人事实缺失，Agent 应指出未知并补充查询或询问。若用户还要求提交申请，再按授权调用业务系统，以实际回执确认结果。

## P12 资料检索、本体与工具怎样配合

资料检索帮助找到相关制度与背景。本体和语义检索提供明确整理的概念、关系与适用说明。工具和业务系统提供具体事实与操作能力。这些能力可以组合，边界也可能重叠，比如本体内容本身可以被检索，工具也可以封装业务规则。这里的分工是为了理解它们在任务中提供的帮助，不是把 RAG 简化成关键词匹配，也不是说每一个任务都必须使用本体。

## P13 多个 Agent 可以引用同一套定义

差旅助手、报表助手和组织助手的问题不同，但都可以使用员工、所属部门和部门负责人的共同定义。每个 Agent 仍保留自己的任务、事实来源和工具。共享定义有助于让业务含义被统一澄清和维护，也方便发现同一个词在不同任务中是否被误用。共享不意味着越过各自权限。要建立这样的共同知识，需要从实际问题出发进行建设。

## P14 一个有用的本体怎样建立

先确定要回答的问题，控制范围。再与资料和业务人员一起确认含义，例如这里的负责人到底是哪种角色。随后建立概念、关系和政策说明，并指出事实来自哪个系统。最后用实际业务问题验证：正常情况下能否解释，必要信息缺失时能否如实指出未知。审批政策可以表达成有明确关联的业务说明，是否进一步编码成可执行逻辑，取决于实际用途。生产者自查与独立业务验证承担不同职责。

## P15 什么时候值得建立本体

本体的价值通常来自业务知识的共享、关系的明确表达以及跨任务复用。如果多个系统和 Agent 反复使用相同的概念，投入可能更有意义。与此同时，模型需要业务澄清、来源连接、验证和维护，这些工作并不会自动消失。对于问题少、变化少且现有文档和工具已经足够的场景，可以先采用更轻量的方式。当共享需求增长，我们需要一个支持这些工作的语义平台。

## P16 OntoWeave：面向 Agent 的业务语义平台

OntoWeave 是面向 Agent 的业务语义平台。外部建模 Agent 与业务人员理解资料、确认含义，平台保存模型，提供确定性校验与受治理读取。业务 Agent 从平台取得相关知识，再通过外部系统查询事实和执行获准操作。这里的模型检查与维护，不表示平台当前提供 OWL 自动推理或业务流程执行引擎。我们用这张简化的图介绍产品职责，接下来看看建设与使用如何衔接。

## P17 在 OntoWeave 中构建与使用语义

构建时，从制度与访谈形成输入，建模 Agent 整理概念、关系与政策说明，提交到平台，再通过业务问题读取与验证。使用时，业务 Agent 围绕当前问题读取相关语义。它得到的可以是审批政策、所属部门关系、负责人含义和人事信息来源，而具体谁担任负责人仍从业务系统读取。这里的四行内容是帮助理解读取结果的教学示意，不是实际接口 JSON 或运行回执。当前模型提交和读回按 R4.3-024/025 路径，真实业务语义效果需要相应验证。

## P18 让 Agent 有明确的业务语义可用

回到三个层次：现实世界是我们要描述和理解的对象，本体是对领域语义的明确建模，RDF、OWL 等技术帮助表达这些知识。Agent 结合语义、当下事实与工具，找到应由李敏审批的依据。我们把业务含义明确表达出来，Agent 就有了一份可以查询、共享和核对的领域知识。OntoWeave 支持的是这份知识的构建、维护与使用。
