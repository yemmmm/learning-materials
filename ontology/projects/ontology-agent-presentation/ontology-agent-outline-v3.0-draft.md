# 本体与 Agent：v3.0 叙事重构草稿

日期：2026-10-15\
形态：逐页内容草稿，供审阅叙事与内容使用。\
建议规模：18 页，约 25–30 分钟。\
听众假设：了解 AI 应用，对知识工程与语义网没有系统背景。

## 这版的讲述思路

全篇围绕一个问题展开：**张三的差旅申请，该由谁审批？**

这件小事足以带出员工、部门、属性、关系、逻辑约定和具体对象，也能展示 Agent 怎样把业务含义与实际数据结合起来。讲述中持续扩展同一个例子，让观众把注意力放在概念上。

整场的推进是：遇到一个业务问题，认识本体，区分本体与表达技术，看懂 Agent 如何使用本体，最后认识支持这件事的平台。

**主视觉锚点是“现实世界—本体—形式表达”三个层次。** 第 4 页建立这张图，第 18 页回到它。知识图谱、Agent 与 OntoWeave 在此基础上解释各自的位置。

本版把 OntoWeave 放在第 16–17 页，用两页介绍定位与使用过程。平台名称可以出现在封面，但产品介绍在概念讲清之后展开。

## 贯穿案例的统一设定

以下全部为虚构教学设定，只用于保持各页一致。

| 项目 | 本例约定 |
| --- | --- |
| 用户问题 | 张三的差旅申请 T-101，该由谁审批？ |
| 本例政策 | 此类差旅申请由申请人当前所属部门的负责人审批 |
| 申请事实 | T-101 的申请人为张三 |
| 组织事实 | 张三属于研发部，直属主管为王强；研发部负责人为李敏 |
| 分类示例 | 经理是一类员工；李敏属于经理 |
| 用于一致性检查的额外约定 | 员工与部门是互斥的类别 |
| 事实来源 | 申请人来自差旅系统，部门归属与负责人来自人事系统 |
| 教学结论 | 按本例政策，应由李敏审批 |

“部门负责人”与“直属主管”是两种不同的业务关系。本例中两者由不同的人担任。“经理是一类员工”只服务于分类与推理示例，审批人的确定依据是具体政策和负责人关系。

## 逐页内容

### P01 本体与 Agent

**本页重点：** 用一个清楚的主题开场。

**上屏内容：** 主标题“本体与 Agent”，副标题“业务含义怎样成为 Agent 可用的知识”。下方放一句“以一张差旅申请为例”。OntoWeave（织义）作为分享项目署名出现。

**画面构想：** 一张简洁的差旅申请单，旁边是“该由谁审批？”的手写式提问。封面只保留一个具体物件和一个问题。

**讲述与衔接：** “我们从一件很普通的事情开始：让 Agent 帮忙找到审批人。”直接进入第 2 页。

### P02 张三的差旅申请，该由谁审批？

**本页重点：** 让观众先感受到业务含义的作用。

**上屏内容：** 展示申请人张三，以及两条组织信息：直属主管是王强，所属研发部的负责人是李敏。旁边放本例政策：“差旅申请由申请人所在部门的负责人审批。”

**画面构想：** 从张三分出两条标有动词的路径。一条连到直属主管王强，另一条经过研发部连到负责人李敏。政策中的“所属部门负责人”与对应路径使用同一强调色。

**讲述与衔接：** 观众通常很快能选出李敏。点明我们刚才做的事：把政策中的概念、关系与具体人员对应起来。这个例子用于揭示判断依据，不演示或声称语言模型必然答错。随后提出：“这些含义，怎样被明确记录和重复使用？”

**左下角小注：** 虚构组织与政策，仅用于教学。

### P03 本体：对领域语义的明确建模

**本页重点：** 给出全篇最重要的定义。

**上屏内容：**

> 本体是对一个领域中概念、关系及其语义约定的明确建模。

用本例解释三个问题：“员工、部门分别是什么？”“申请人与部门怎样关联？”“哪些分类和关系具有确定的含义？”

**画面构想：** 从第 2 页的人名图中淡出具体姓名，留下员工、部门、差旅申请，以及申请人、所属部门、负责人这些关系。让观众看到抽象是怎样发生的。

**讲述与衔接：** 业务里默认理解的词语，通过建模变成可以共同引用的定义。模型只选择当前用途需要表达的那部分领域知识。下一页区分现实中的业务、我们建立的模型，以及模型的表达方式。

**左下角小注：** 本演示讨论知识工程中的本体（Ontology）。

**讲者依据：** 定义采用面向入门听众的概括，参考 [Gruber 的 Ontology 定义](https://tomgruber.org/writing/definition-of-ontology/)。哲学中的“本体论”只在口头解释这一用语背景时简要提及。

### P04 现实世界、本体、形式表达

**本页重点：** 建立后面所有内容的认知框架。

**上屏内容：** 三个横向区域，每个区域只有一个问题和一个例子。

| 层次 | 回答的问题 | 本例 |
| --- | --- | --- |
| 现实世界 | 实际发生了什么？ | 张三属于研发部，提交了一张差旅申请 |
| 本体 | 我们怎样理解这个领域？ | 员工、部门、申请及其关系与语义约定 |
| 形式表达 | 怎样把这些含义明确表达出来？ | RDF、OWL 或其他约定的表达方式 |

**画面构想：** 左侧是人员与申请单，中间是概念关系图，右侧是少量结构化表达。左到中的连接标“观察与抽象”，中到右标“编码与表达”。中间区域最突出。

**讲述与衔接：** 同一套业务理解可以通过不同方式表达。本体关注我们究竟表达了什么含义。先认识模型的组成，再讨论表达技术。

**讲者备注：** 三个层次是教学上的区分。实际保存的本体产物当然有具体表达形式；此处强调语义模型与所选表达技术可以分别讨论。

### P05 本体的常见组成

**本页重点：** 把用户给出的五项组成变成一张能看懂的模型。

**上屏内容：** 在同一幅图上逐项点亮五类内容，旁边保留简短图例。

| 组成 | 本例 | 作用 |
| --- | --- | --- |
| 类（Class） | 员工、经理、部门、差旅申请 | 定义概念与类别 |
| 属性（Property） | 姓名、入职时间 | 描述对象的特征 |
| 关系（Relation） | 员工隶属于部门 | 描述对象之间的联系 |
| 公理（Axiom） | 经理是一类员工 | 明确具有逻辑含义的断言 |
| 个体（Individual） | 张三、李敏、研发部 | 表示具体对象 |

**画面构想：** 类画成轮廓，个体画成实心标记，属性贴在对象旁，关系在线上标动词，公理用分类连接表达。采用逐步显现，让观众看到各部分各自做什么。

**讲述与衔接：** 按用途选取需要的内容，核心是把语义说清楚。先澄清最容易混淆的一组：员工这个概念和张三这个人。

**左下角小注：** 这些是常见组成。OWL 中，对象之间的关系通常也属于 Property。

### P06 “员工”与“张三”处在不同层次

**本页重点：** 区分一般定义与具体事实。

**上屏内容：** 上方展示“员工”“部门”及“所属部门”关系的定义，下方展示事实“张三属于研发部”“研发部负责人是李敏”。用“属于这个类别”的虚线把张三连到员工，把研发部连到部门。

**画面构想：** 上半页标“一般定义”，下半页标“具体事实”。随后将李敏替换为另一位负责人作为变化示意，上面的概念与关系含义仍然适用。

**讲述与衔接：** 定义能够被许多具体对象复用。具体事实可以按需要纳入知识系统，也可以保留在原业务系统中，使用时再读取。下一页看这些知识怎样被技术表达。

**左下角小注：** 个体可按需纳入；本体建设不要求复制全部业务数据。

**讲者备注：** 这里区分的是定义与事实的作用，不能据此将本体限定为“只能有类”，也不能将知识图谱限定为“只能有实例”。

### P07 RDF 与 OWL 分别做什么

**本页重点：** 给技术名词一个足够直观的位置。

**上屏内容：** 左侧 RDF：用可连接的图陈述知识，例如“张三—所属部门—研发部”。右侧 OWL：为类、关系及其组合提供形式语义，例如“员工与部门互斥”。下方一句：“这些技术帮助我们把语义模型表达为可被软件处理的知识。”

**画面构想：** 同一段知识从中文说明过渡到图，再突出具有逻辑含义的声明。屏幕只放一条三元组示意和一条语义声明。

**讲述与衔接：** RDF 是图数据模型，OWL 是本体语言，两者可以一起使用。采用标准表达以后，软件就能按明确语义处理其中一些逻辑关系。

**左下角小注：** RDF/OWL 各有职责，并非两种互斥的文件格式。

**讲者依据：** 参考 [W3C RDF 1.1 Primer](https://www.w3.org/TR/rdf11-primer/) 与 [W3C OWL 2 Primer](https://www.w3.org/TR/owl2-primer/)。RDF 可以表达事实和定义；RDFS 已提供基础分类词汇。JSON 等数据格式也可以承载表达，其业务含义需要相应约定。这些补充不展开为新的技术清单。

### P08 形式语义怎样支持推理与检查

**本页重点：** 用实际变化解释“形式化”的价值。

**上屏内容：** 主图展示一个推导：已知“经理是一类员工”和“李敏是经理”，可以推出“李敏是员工”。旁边用一个较小的错误例子展示检查：若已声明员工与部门互斥，却把张三同时标成员工和部门，会产生逻辑矛盾。

**画面构想：** 已知知识使用常规色，推导结果使用强调色。错误例子单独标“假设误录”，避免与贯穿案例的正常事实混在一起。

**讲述与衔接：** 这里的推理，是根据形式语义计算逻辑后果。它支持一些明确的检查与推导，业务数据是否真实仍需相应依据。接下来区分另一个经常一起出现的概念：知识图谱。

**左下角小注：** 自动推导需相应形式表达与推理工具；能力依表达范围而定。

**讲者依据：** 参考 [OWL 2 Primer 的基础知识建模部分](https://www.w3.org/TR/owl2-primer/#Modeling_Knowledge:_Basic_Notions)。此页说明通用技术能力，不作为 OntoWeave 当前功能演示。

### P09 本体与知识图谱怎样配合

**本页重点：** 将三个容易混淆的概念分别定位。

**上屏内容：**

- 本体：明确员工、部门、负责人等概念和关系的含义。
- 知识图谱：把有关人员、组织、申请等知识组织成相互连接的网络。
- RDF/OWL：可以参与这些知识的技术表达。

**画面构想：** 同一张图中，上部保留概念定义，下部连接张三、研发部、李敏和申请 T-101。用注释说明本体提供语义定义，整张知识网络可以同时包含定义和事实。表达技术作为图外的小标签。

**讲述与衔接：** 观众到这里应能分清“表达什么含义”“怎样组织知识”“采用什么技术”。随后讨论 Agent 怎样取用这些知识。

**左下角小注：** 知识图谱可包含本体定义，也可采用不同图技术。

**讲者依据：** 知识图谱的模式、身份与图表示关系参考 [Hogan 等《Knowledge Graphs》](https://arxiv.org/abs/2003.02320)。图中的上下布局用于说明作用，不规定产品必须分成两个存储层。

### P10 本体在 Agent 体系中的位置

**本页重点：** 解释业务任务需要哪些不同来源的能力。

**上屏内容：** 让用户问题进入中央的 Agent。围绕它展示四项分工：语言模型理解请求并组织判断；本体提供明确的业务定义与关联；业务系统提供当前事实；工具提供查询、计算和执行能力。

**画面构想：** 中央是使用语言模型的 Agent。左侧连接语义模型，右侧连接业务数据与工具。连接线上写“查定义”“取事实”“调用能力”。让本体成为 Agent 可访问的知识来源。

**讲述与衔接：** 通用语言能力需要结合具体组织的约定与当下事实。拿到这些输入后，Agent 如何解决开场问题？下一页完整走一次。

**讲者备注：** 本图是面向业务应用的概念分工，不规定所有 Agent 必须采用同一技术架构，也不表示本体直接改变语言模型的参数。推理器可以作为可选工具接入。

### P11 Agent 如何找到审批人

**本页重点：** 用一条可核对的路径闭合开场问题。

**上屏内容：** 按四步展开。

1. **取得语义：** 此类差旅由申请人当前所属部门的负责人审批，理解“申请人”“所属部门”“负责人”各自的含义及关联。
2. **查询事实：** 差旅系统返回 T-101 的申请人张三，人事系统返回张三属于研发部、研发部负责人为李敏。
3. **结合政策判断：** 沿“申请—申请人—所属部门—负责人”找到李敏。
4. **给出答案与依据：** “按本例政策，应由研发部负责人李敏审批。张三属于研发部，李敏当前担任该部门负责人。”

**画面构想：** 上方是一条政策，下方是一条标出来源的事实路径。最后收敛成一段简短答复。王强的直属主管关系保留为浅色分支，帮助观众看到为什么选用当前路径。

**讲述与衔接：** 这个过程由 Agent 结合语义和事实完成。若负责人信息缺失，就说明缺少什么并继续查询或询问。若任务进一步要求提交，再按授权调用业务系统并核对回执。下一页看资料检索与工具怎样参与其中。

**左下角小注：** 教学推演，未调用真实业务系统。

### P12 资料检索、本体与工具怎样配合

**本页重点：** 让听众理解不同方法可以组合使用。

**上屏内容：** 围绕同一个审批问题展示三种输入。

| 方式 | 给 Agent 带来什么 | 本例 |
| --- | --- | --- |
| 资料检索（如 RAG） | 找到相关材料与上下文 | 找到差旅制度中的审批条款 |
| 本体与语义检索 | 提供明确的定义、关系与适用说明 | 识别“所属部门负责人”对应的业务路径 |
| 工具与业务系统 | 取得实时事实，完成获准操作 | 查询当前负责人，提交差旅申请 |

**画面构想：** 三路内容汇入同一个 Agent。每路显示一条很短的真实含义示例，避免只排列技术名称。

**讲述与衔接：** 本体能让经常使用的业务含义被显式整理和共同维护。检索与工具继续提供材料、事实和能力。多位 Agent 使用同一套业务定义时，这种组织方式的价值更容易体现。

**左下角小注：** 这些能力可以重叠组合，本体内容也可以成为检索对象。

**讲者备注：** 这是本演示对应用分工的归纳，不是互斥的技术分类。避免把 RAG 描述成只能做关键词匹配，也不声称本体是减少所有业务错误的必要条件。

### P13 多个 Agent 可以引用同一套定义

**本页重点：** 把价值从单次回答扩展到跨任务复用。

**上屏内容：** 中间保留同一组“员工、所属部门、部门负责人”定义，周围出现三个任务：差旅助手查审批人，报表助手按申请人所属部门统计申请数，组织助手查部门负责人。

**画面构想：** 三个任务连接到同一份语义模型，再分别连接自己的事实来源与工具。只突出共同引用的概念及关系。

**讲述与衔接：** 不同任务可以共同引用业务含义，同时保留各自的流程与能力。为了做到这一点，模型中的定义需要事先澄清，并在业务变化时维护。接下来介绍怎样建立它。

**左下角小注：** 共享定义的读取仍遵循各自权限与适用范围。

### P14 一个有用的本体怎样建立

**本页重点：** 给出一条观众可以记住的建设路径。

**上屏内容：** 五个连续步骤，每步只配一个本例中的动作。

| 步骤 | 本例 |
| --- | --- |
| 从问题确定范围 | 要回答“这张差旅申请由谁审批” |
| 与业务人员澄清含义 | 负责人指部门负责人，还是直属主管？ |
| 建立概念、关系与语义说明 | 员工、部门、申请、所属关系及审批政策 |
| 连接事实来源 | 申请人查差旅系统，组织关系查人事系统 |
| 用业务问题验证 | 正常情况能解释，缺少负责人时能指出未知 |

**画面构想：** 一条从问题开始、回到问题的开放环形路径。每一步让第 2 页的示意图增加一部分明确知识。

**讲述与衔接：** Agent 可以协助读材料、整理关系与检查遗漏，业务含义仍需要资料和领域人员确认。模型是否有用，要回到实际问题评估。下一页说明怎样判断这项投入是否值得。

**讲者备注：** 本页给出简化的工程方法。审批政策可作为有明确关联的业务说明表达，是否进一步编码为可执行逻辑取决于用途。生产者自查和独立业务验证承担不同职责。

### P15 什么时候值得建立本体

**本页重点：** 给观众一个务实的使用判断。

**上屏内容：** 重点呈现三种需要：多个任务反复使用同一套概念，业务问题依赖跨对象或跨系统的关系，业务定义需要长期维护。旁边用一行指出建设投入：“需要持续澄清含义、连接来源、验证和维护。”

**画面构想：** 从一项孤立问答扩展到多个业务任务，共用的概念逐渐显现。画面侧边保留清晰的维护工作说明。

**讲述与衔接：** 问题少、变化少、现有文档和工具已能清楚支持任务时，可以采用更轻量的组织方式。跨任务共享需求增长时，显式语义模型更值得考虑。由此自然引出：怎样为构建和使用这些模型提供一个工作平台？

### P16 OntoWeave：面向 Agent 的业务语义平台

**本页重点：** 用已经理解的概念介绍产品定位。

**上屏内容：** 一句话：“OntoWeave 连接构建领域语义的人与 Agent，以及使用这些语义的业务 Agent。”平台内部只展示三件事：保存概念与关系，支持模型维护与检查，按权限提供相关语义。

**画面构想：** 左边是业务人员与建模 Agent，中间是 OntoWeave 中的领域语义模型，右边是消费语义的业务 Agent。业务数据与执行系统放在右下方，与业务 Agent 连接。

**讲述与衔接：** 外部 Agent 负责理解材料和建模判断，平台承接模型的保存、校验与读取。使用方取得语义后，再结合业务系统完成任务。下一页用两个连续过程说明它如何工作。

**左下角小注：** 平台定位示意；业务数据查询与动作执行由外部能力承担。

**讲者依据：** 产品定位参考项目 README（原项目 `ontology-platform/README.md`），语义读取与当前能力范围参考 v4.0 需求（原项目 `ontology-platform/docs/requirements/requirements-v4.0.md`）中的 R4.0-008、R4.0-025。此处“检查”指模型写入等平台检查和配套的业务验证工作，不表示当前提供 OWL 自动推理。介绍不附未经验证的准确率或成熟度结论。

### P17 在 OntoWeave 中构建与使用语义

**本页重点：** 展示平台承接的完整使用过程。

**上屏内容：** 上下两条路径，共用中间的一份模型。

- **构建时：** 制度与业务访谈形成输入，建模 Agent 整理员工、部门、申请及政策的含义，提交到平台，再用业务问题读取和验证。
- **使用时：** 业务 Agent 接到审批问题，读取相关定义、关系、政策说明与事实来源，再通过外部工具取得人员信息，给出解释或完成获准操作。

**画面构想：** 上方的建设路径把知识送入平台，下方的使用路径从平台取用知识。放大一次语义读取，显示“审批政策、所属部门关系、负责人含义、人事信息来源”四行示意内容。

**讲述与衔接：** 让观众具体看到平台提供给 Agent 的内容。读取到的领域语义，与当前事实共同支持最终回答。最后回到三个层次，重新看待整件事。

**左下角小注：** 流程与读取内容为教学示意，非真实运行回执。

**讲者依据：** 当前模型提交与读回路径参考 v4.3 需求（原项目 `ontology-platform/docs/requirements/requirements-v4.3.md`）中的 R4.3-024/025。内容准确性和语义效果需相应业务验证。此页以定位和工作过程为主，省略 Team 内部角色、数据库组件和接口参数。

### P18 让 Agent 有明确的业务语义可用

**本页重点：** 让听众带走一个稳定的理解。

**上屏内容：** 回到第 4 页的三个层次，保留三句话：

> 现实世界，是我们要描述和理解的对象。\

**画面构想：** 第 4 页的三个区域原位出现，观众已能读懂其中内容。下面是缩小后的审批路径与“李敏”的答案，通过上下呼应形成结束画面。
