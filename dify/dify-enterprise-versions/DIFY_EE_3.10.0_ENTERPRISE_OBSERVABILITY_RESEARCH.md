# Dify Enterprise 3.10.0 企业可观测性特性调研

> 调研日期：2026-07-28  
> 适用版本：Dify Enterprise 3.10.0（社区版基线 1.14.1，企业层 0.17.0）  
> 资料范围：Dify Enterprise 官方 3.10.0 发布说明及其部署说明

## 结论摘要

3.10.0 将企业后端服务的可观测性从分散日志、组件级排障推进到 **基于 OpenTelemetry（OTel）的统一 Trace 与 Metric 输出**。该版本会为两类关键内部路径产生遥测数据：

- **远程调用**：用于观察服务间或外部依赖调用的延迟与失败；
- **数据库访问**：用于定位查询、连接或数据库依赖造成的性能瓶颈。

它是面向生产运维的基础设施能力，而不是新的 Dify 业务分析页面。数据通过标准 `OTEL_*` 环境变量导出至组织已有或选定的 OTel Collector / 后端；官方已同步更新 Helm Chart 和 Docker Compose 模板。

## 1. 版本定位与能力边界

官方将 3.10.0 标记为维护版本（Maintenance）且不可跳过（Non-skippable）。除可观测性外，本版还引入 Redis Sentinel、部分 Redis Cluster、外部 PGVector、插件 HPA 和 kubeconfig 动态令牌轮换等生产部署能力。

本调研只覆盖“企业可观测性”新增能力，边界如下：

| 范围 | 3.10.0 已提供 | 不应误解为 |
| --- | --- | --- |
| 遥测信号 | 后端对远程调用、数据库访问输出统一 OTel Trace 和 Metric | 自动提供完整的业务 KPI、审计报表或告警规则 |
| 配置接口 | 标准 `OTEL_*` 环境变量；Helm 与 Docker Compose 已有模板入口 | 每一种 OTel 后端均有 Dify 专属配置页 |
| 数据去向 | 对接 OTel Collector 或兼容的观测后端 | Dify 在自身数据库中替代专业可观测平台 |
| 诊断重点 | 跨服务链路、依赖耗时、异常与数据库瓶颈 | 仅凭 Trace 即可替代日志、指标告警和 SLO |

## 2. 截至 3.11.1：可从该能力获得哪些 Dify 信息

下表按官方发布说明逐项收敛能力范围。这里的“可获得”指 Dify 已产生/导出的遥测或可用于关联的上下文；具体字段名、维度和展示形式取决于 3.11.1 部署模板、OTel Collector 处理规则及选用的观测后端，不能把未公开的 Span 属性当成稳定契约。

| Dify 信息或观测视角 | 截至 3.11.1 的能力 | 能用于回答的问题 | 版本来源 | 边界与注意事项 |
| --- | --- | --- | --- | --- |
| 企业后端的远程调用路径 | 企业后端会为远程调用输出统一 OTel Trace 和 Metric。 | 哪一段远程依赖路径参与了请求；该路径是否成为性能或故障排查对象。 | 3.10.0 新增。 | 官方未在发布说明中承诺完整 Span 属性、所有协议覆盖范围或现成看板；延迟、错误等具体查询取决于导出内容和后端建模。 |
| 企业后端的数据库访问路径 | 企业后端会为数据库访问输出统一 OTel Trace 和 Metric。 | 请求慢是否与数据库访问链路有关；数据库路径是否值得结合慢查询、连接池和资源指标继续排查。 | 3.10.0 新增。 | 不是数据库性能分析器，也不替代 PostgreSQL 慢查询、锁等待、SQL 执行计划或主机监控。 |
| 知识库 / RAG 检索过程 | 文档检索步骤可追踪；发布说明同时明确 RAG 知识检索管线具有 OTel tracing span。 | 某次回答是否经过检索；检索路径是否可能造成知识召回延迟或透明度问题。 | 3.11.0 明确“document-retrieval steps are traceable”；3.9.6 已引入 RAG retrieval OTel spans。 | 官方没有承诺在 OTel 中自动暴露原始文档内容、完整检索结果、分数、用户问题或提示词；敏感内容是否记录由实际埋点与脱敏策略决定。 |
| 一组业务调用的关联标识 | 可以为 Phoenix 设置自定义 trace session ID。 | 如何把同一业务会话、一次外部工单或一组相关调用归在一起检索。 | 3.11.0 新增。 | 这是关联/检索上下文，不是新指标；ID 的命名、注入方式和保密性需由团队规范，避免放入个人信息或敏感业务编号。 |
| 应用 Trace 配置的权限归属 | Trace 配置端点具备租户隔离；3.11.1 进一步要求修改 Trace 配置具有编辑权限。 | 谁能修改某工作区/应用的 Trace 配置，是否能跨租户越权修改。 | 3.9.5 安全修复；3.11.1 RBAC 权限修正。 | 这是治理与访问控制信息，不是一次运行的业务遥测数据。 |
| 应用日志的可见性 | 3.11.1 修正为编辑者可以查看应用日志。 | 在 Trace 发现异常后，具备权限的编辑者能否继续查看应用日志进行交叉排障。 | 3.11.1 修复。 | 应用日志是与 OTel 互补的信号，不代表日志已自动注入 trace_id，也不代表它由 OTel 指标系统提供。 |

### 3.11.1 的结论

3.11.1 **没有发布新的 OTel 信号类型或新的指标体系**。截至该版本，可观测能力的增量重点是：3.10.0 覆盖企业后端远程调用和数据库访问；3.11.0 补足 RAG 检索可追踪性与 Phoenix 自定义会话关联；3.11.1 主要改善 Trace 配置权限和日志查看权限。因此它仍应被视为“Dify 向外部观测平台提供的标准遥测数据源”，而非 Dify 内置的全功能监控产品。

### 当前不能直接承诺的信息

根据已核对的官方 3.10.0～3.11.1 发布说明，不能直接承诺该能力会自动提供：

- 每个应用、工作流、模型、用户、Token 消耗或成本的预制指标看板；
- 原始 Prompt、模型输出、检索文档正文、完整 SQL 或其他敏感内容；
- 现成的告警规则、SLO、留存策略、日志索引或根因诊断结论；
- 不经 Collector/观测后端配置就能在 Dify 内部查看的 Trace 浏览器。

若这些信息是验收目标，应先在目标 3.11.1 环境抓取一条真实 Trace 与 Metric，再把实际属性清单固化为企业自己的遥测契约和脱敏规则。

## 3. 能解决什么问题

### 3.1 请求慢但难以归因

一次工作流或管理操作耗时变长时，Trace 可以把一次请求展开为调用链。运维人员能够区分时间主要耗在远程服务、数据库访问还是本服务逻辑，而不是只看到一个总耗时。

### 3.2 外部依赖间歇失败

远程调用的 Trace 与 Metric 便于按依赖、状态和耗时观察失败模式，并与 Collector/观测后端中的错误、重试或告警关联。它特别适合排查“偶发超时”“仅某一依赖变慢”等生产问题。

### 3.3 数据库成为隐性瓶颈

数据库访问进入统一遥测面后，可以与同一请求的其他 Span 对照，确认慢请求是否集中在数据库路径。后续仍需要结合 PostgreSQL 慢查询、连接池和主机资源指标作根因判断。

## 4. 推荐接入架构

```text
Dify Enterprise 后端服务
    │  OTLP（Trace / Metric）
    ▼
OpenTelemetry Collector
    ├── Trace 后端（链路检索、调用树、错误定位）
    ├── Metric 后端（看板、告警、SLO）
    └── 可选：日志后端（与 trace_id 关联）
```

建议将 Collector 作为网络、鉴权和采样策略的统一边界：Dify 只负责产生与导出标准遥测数据；批处理、脱敏、采样、路由、多后端投递和告警规则由 Collector 与观测平台负责。

## 5. 配置与上线要点

### 5.1 通过标准 OTel 环境变量配置

官方明确说明本能力通过 `OTEL_*` 环境变量配置，但发布说明没有给出一组可直接照抄的完整变量清单。因此实际部署应以 **3.10.0 随附的 Helm values / Docker Compose env 模板**为准，按企业选用的 Collector 协议、端点、TLS 和认证方式填值；不要从其他版本或其他产品复制变量名。

上线前应确认：

1. Collector 的 OTLP 接收端点、DNS、网络策略和证书链均可从 Dify Pod/容器访问。
2. Trace、Metric 的导出开关和端点均已按 3.10.0 模板配置，敏感认证信息使用 Secret 管理。
3. 资源属性能够区分环境、集群、服务和版本；避免把用户输入、凭据、完整提示词或其他敏感业务字段写入遥测属性。
4. 采样率、批处理大小和超时有容量依据；故障时遥测导出不应阻塞关键业务请求。

### 5.2 Helm 与 Docker Compose

两种官方部署模板都已更新，配置入口是同一能力而非两套不同产品实现：

- **Helm**：将 OTel 配置写入受版本管理的 values 文件，并通过 Kubernetes Secret 引用令牌或证书；部署后核对目标工作负载的实际环境变量。
- **Docker Compose**：使用 3.10.0 包中的环境文件结构与 Compose 模板，避免仅覆盖旧 `.env` 而遗漏新版模板中的遥测配置入口。

### 5.3 端点格式兼容性修复

3.10.0 同时修复了 OTLP endpoint 校验：此前含 `http://` 或 `https://` scheme 的完整 URL 会被错误拒绝；现在可正确接受。这使需要完整 URL 的观测服务（官方举例为 Alibaba Cloud ARMS）能够接入。该修复不表示可以忽略协议、证书或认证校验。

## 6. 验收建议

建议用一个可控请求做端到端验收，而不是只检查容器启动成功：

| 验收项 | 预期结果 |
| --- | --- |
| 导出连通性 | Collector 收到目标服务的 Trace 与 Metric，且无持续导出错误 |
| Trace 完整性 | 单次请求可看到远程调用和数据库访问相关 Span，并保留正确父子关系 |
| 属性治理 | service/environment/version 等资源属性正确；无密码、Token、原始敏感输入等泄露 |
| Metric 可用性 | 观测后端可按服务和环境查询延迟、错误等遥测指标 |
| 故障韧性 | 暂停或拒绝 Collector 时，Dify 业务请求不会被遥测发送显著阻塞 |
| 升级兼容 | 使用目标 3.10.0 Helm/Compose 模板重建后，配置仍生效 |

## 7. 升级关联风险

3.10.0 是不可跳过版本，升级前必须备份 PostgreSQL 与 Redis，并检查集群滚动升级资源。若使用自定义 Redis/Sentinel，还需先审阅本版统一 Redis/MQ 配置模型。可观测性接入本身不替代这些升级动作。

此外，本版含 Dify 数据库 `model_type` 兼容迁移与 Docker Compose `env_file` / `envs/enterprise/*` 架构变化。升级后出现“遥测不生效”时，应先核实是否采用了目标版本的部署模板和环境文件，而不是立即判断为 Collector 故障。

## 8. 采用建议

建议按“先可见、再治理、后告警”的顺序推进：

1. 先把一个非生产或低风险环境接入 Collector，确认 Trace 与 Metric 实际到达。
2. 建立服务、环境、版本等统一资源属性和敏感字段脱敏规则。
3. 基于一段稳定观测期的数据设置延迟、错误率和 Collector 导出失败告警。
4. 将关键 Trace 与应用日志、数据库慢查询和基础设施指标关联，形成排障 Runbook。
