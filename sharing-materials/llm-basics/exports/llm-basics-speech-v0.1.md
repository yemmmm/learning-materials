## P01 大模型常见概念

大家好，今天我们做一次大模型常见概念的扫盲。大家不需要有机器学习背景，只需要带着自己用 AI 时遇到过的问题来听：为什么它会忘记前面说过的话，为什么有时候一本正经地说错，为什么加上知识库之后还是答不对，以及一个 Agent 为什么会比一次聊天慢很多。

我们会用一个很普通的场景贯穿全程：员工在家连不上公司内网，希望 IT 助手提供帮助。最开始它只会解释，后来可以查公司文档，再后来能查服务状态、创建工单。随着这个助手一步步增加能力，相关术语就有了具体位置。今天的目标是大家听完之后，能解释自己看到的现象，也能和同事讨论一个 AI 功能到底需要哪些组件。

## P02 今天沿着八个问题往下走

今天按八个问题展开。前半部分围绕日常使用：先分清模型和应用，再理解模型一次能看到什么，以及我们怎样把需求表达清楚。接着讨论看图、联网和推理各自补充了什么能力。

后半部分进入应用开发。我们给 IT 助手接入公司资料和业务工具，然后看调用成本、等待时间与评测。演示会穿插在中间：先看真实分词结果，再比较提示与资料的作用，最后走一遍工具调用到工单结果。延伸词汇放在附录，现场有兴趣再展开。这份材料是初稿，六十分钟包含演示、停顿与听众互动，正式分享前可以按实际语速调整。

## P03 你用的是应用，应用里面有模型

先分清两个词：模型与应用。我们打开一个聊天网页，实际使用的是应用。模型是这个应用的重要组成部分，但页面、文件上传、聊天历史、搜索、工具调用和业务流程，都需要应用来组织。

从概念范围看，人工智能很宽，机器学习是其中一条路线，深度学习是机器学习的一类。今天常见的大语言模型大多建立在深度学习基础上。生成式 AI 关注生成内容，除了语言，还可以是图片和声音；不要把所有生成式系统都直接叫作大语言模型。

为什么同一个模型在代码工具里很好用，在一个简单聊天框里却不方便？因为前者可能知道当前项目、文件和错误信息，还能运行命令；后者可能只收到你输入的一句话。遇到体验差异时，我们要同时看模型和外围应用。

## P04 训练在改变模型，推理在使用模型

训练可以先理解成学习阶段。预训练让模型从大量数据中学习语言、知识和各种模式；后训练继续改善它遵循要求、完成任务等方面的表现。训练的关键特征是会调整模型参数。

推理是把已有模型拿来使用。对常见的自回归语言模型，系统输入一段上下文，模型预测并生成接下来的 Token，再基于已有内容继续生成。这个基础方式可以支撑写作、代码和许多推理任务，但不等于模型只会机械复制训练原文。

我们在对话中纠正了一个错误，它可能在下一轮照着修正，这是因为纠正内容进入了上下文。它也可能被应用保存为记忆。至于这些数据日后是否被服务商用于训练，是另外的数据使用问题，不能从“这次记住了”就判断模型权重已经改变。下一步我们看看刚才反复出现的 Token 是什么。

## P05 Token：模型处理文字的基本单位

Token 可以理解为模型处理文字时使用的小片段。我们平时按汉字、单词或者字符计数，模型使用的是自己的分词器，因此这些单位之间没有固定的一一对应关系。

【演示约两分钟】先看“今天开会。”，再切换到英文 Hello, world!，最后看一行代码。请大家留意，英文中的空格可能和后面的词放在同一个 Token 中，代码里的括号和引号也可能合成一个片段。这里用了 tiktoken 的 cl100k_base 编码，所有结果已经真实计算并保存；它只是一个具体示例，不代表所有模型的分词方式。中文也可能出现一个字跨多个 Token 的情况，不能从这个短句推出一字一 Token 的规则。

为什么要认识它？因为上下文上限、模型用量和很多服务的计费都和 Token 有关。估算可以帮助建立直觉，接入具体接口时仍应按对应分词器或用量返回值核对。

## P06 模型每一轮看到的，比聊天框更多

聊天框只显示我们能看到的一部分。一次实际调用，可能还带有系统指令、历史消息、检索资料、工具说明和工具返回。Prompt 在宽泛用法里，就是提供给模型的输入；在消息接口中，这些内容往往按角色和类型组织。

上下文窗口限制模型一次能处理多少信息。这里的具体口径要看接口：输入与输出如何分配，是否存在单独的输出上限或推理预算，都可能不同。对日常使用来说，先记住所有这些信息都不是无限的。

长对话会忘记事情，有时是应用没有把旧内容带过来，有时是已经压缩成摘要，有时是虽然还在上下文里，却没有被准确利用。把聊天历史存下来、把它装进当前请求、以及模型真正用对它，分别需要不同能力。诊断问题时，可以先问一句：相关信息这轮到底有没有送到模型面前？

## P07 记忆：应用保存，再适时拿出来

现在把记忆拆成几层。当前上下文，是这一次模型正在看的材料。聊天记录，是应用保存的历史。长期记忆，可能是从历史中提取出来的偏好、任务摘要和事实，下一次按需要检索回来。模型参数则是在训练中形成的，它不是一份可以逐条查阅的个人聊天数据库。

比如我今天告诉助手，以后把结果整理成表格。应用可以把这个偏好保存下来，下次调用时再放到上下文里，模型就表现得像是记住了我。这种实现不需要在每次聊天之后重新训练模型。

不同产品对记忆的实现不同，有的保存原文，有的提取摘要，有的只保留一部分。所以“开启记忆”也不表示什么都能记住。对企业应用，我们可以进一步追问：保存了什么、何时取出、过期信息如何更新。这些都是应用层的问题。

## P08 先把“帮我整理一下”变成明确任务

假设我们把一段会议记录交给 AI，只说“帮我整理一下”。它给一个概括，或者列一堆事项，都可能符合这句要求。我们没有告诉它哪些内容必须提取，也没有说能不能补全缺失信息。

【演示约两分钟】先看模糊要求，再切到明确任务：提取决策、负责人和截止时间，缺失字段写“未提供”，只根据会议原文，用表格组织。这样结果才更接近可以交接的任务清单。原文没有给具体日期，也没有给第二项负责人，就应该保留缺失，而不是猜出一个人名和日期。

最后补充公司事项分类表，让它按故障、变更、咨询分类。这里增加的是完成任务所需的外部信息。任务要求解决“要做什么、怎么交付”，参考资料解决“依据什么”。页面输出是事先编写的教学对照，不是现场调用模型，也不是效果保证。真正使用时还要检查结果。

## P09 提示工程与上下文工程各管什么？

Zero-shot 和 Few-shot 描述的是两种常见提示方式。Zero-shot 直接讲规则，不给任务示例；Few-shot 则补充少量输入和对应输出，让模型看到我们想要的标准。这里的示例放在上下文中，并不表示已经做了一次微调。

Prompt Engineering 主要关注如何写清、组织好指令。Context Engineering 的范围更宽：除了指令，还有哪些资料、历史消息、工具说明和执行结果应该出现在本轮调用中？执行下一步之后，又应该怎么更新？

拿 IT 助手来说，用户问 VPN 故障，不需要把整个公司的所有制度塞进去；更有用的是相关指南、当前服务状态和必要的用户信息。信息越多并不自动越好，关键是相关、清晰、及时。在后面的 RAG 和 Agent 章节，我们会看到上下文工程在应用里怎样落地。

## P10 随机性、格式正确、事实正确是不同维度

Temperature 是很多文本生成接口中的采样参数。可以粗略理解为，它影响模型在候选输出之间选择时的随机程度。较低值通常更集中，较高值往往更发散。但不同模型支持的参数不同，具体要看接口文档。即使参数很低，也不应该把输出视作绝对稳定，更不能据此保证事实正确。

再看结构化输出。人工阅读一段话很方便，程序更希望拿到固定字段，比如决策、负责人和截止时间。只在提示里写“请输出 JSON”，是提出一个要求；接口提供 JSON Schema 之类的约束，才是另一种结构保障。

即使字段和类型都符合约定，里面的负责人仍可能填错。比如一个合法字符串“小王”，可能根本不在会议原文里。因此结构校验和业务内容核对要分开。解析成功，说明数据能被程序读入；并不说明任务已经做对。

## P11 看图、联网、深度思考分别增加了什么？

看图、联网和深度思考，听起来都在让 AI 更强，但它们增加的东西不同。多模态让系统接收或生成更多形式的信息。能看截图，不意味着它能生成图片；某个产品能生图，也可能是调用了另外的生成模型。

联网是在本次调用中获取外部信息。模型训练中形成的知识有时间边界，实时服务状态、本周公告之类的信息需要外部来源。搜索结果也可能过时、无关或不可靠，所以联网不是事实正确的自动保证。

推理模型和思维链主要涉及多步求解。CoT 是 Chain of Thought 的缩写，可以帮助理解把求解过程拆成步骤的方式，但产品展示的思考文字不能单独证明结果成立。我们可以拿排障打比方：看图提供输入，查资料提供证据，推理把线索连起来，最后仍要通过运行或其他结果来验证。

## P12 幻觉：话很完整，依据却可能不存在

幻觉是指模型生成了看似合理、实际没有依据或不成立的内容。开发场景里，它可能编出一个不存在的函数；排障场景里，它可能只看到一个报错，就断定整个服务器缺了依赖。

比如这里导入 yaml 失败，说明当前执行环境没有成功找到这个模块。可能没有安装，也可能装在另一个环境里，或者启动程序使用了不同解释器。截图能支持的结论有限，我们不要把它自动扩展成更大的事实。

实用做法是分三栏：已确认什么，正在假设什么，下一步怎样验证。需要版本信息就补版本，需要官方文档就找文档，需要运行检查就检查。要求模型给来源是一个起点，还要确认来源确实存在、内容确实支持当前结论。顺畅的语言可以帮助表达，但不能代替证据。

## P13 RAG：先查资料，再带着资料回答

如果模型没见过公司的内部文档，怎样让它回答公司特有的问题？一个常见方案是 RAG，中文叫检索增强生成。先根据用户问题找到相关资料，再把资料和问题一起交给模型生成回答。

用户问“在家连不上内网怎么办”，系统先查到远程接入指南里的相关章节，再据此说明检查步骤，并关联来源。这里的知识是本次提供给模型的，不需要因为每次更新文档就重新训练整个模型。

RAG 也有边界。如果文档只讲配置步骤，里面没有当前服务状态，那么模型不能从文档里得出“现在服务正常”。它需要另外查询。回答中带了来源，也要检查那段来源是否真的支持结论。RAG 把回答和资料连接起来，效果还取决于检索是否命中，以及模型有没有正确使用资料。

## P14 Embedding：让“意思接近”可以被检索

Embedding 可以先理解成一种文本表示方法：把一段内容转换为一组数字，也就是向量。表示得合适时，意思接近的内容在向量空间里往往也更接近，因此可以用来检索。

这对口语化提问很有帮助。用户说“在家连不上内网”，文档标题却是“远程接入配置指南”，两者没有完全相同的词，语义检索仍有机会把它们关联起来。但这不是必然保证，效果和模型、切分、数据与查询都有关系。

关键词检索也很有用，尤其是错误码、订单号、产品名等精确内容。很多系统会组合关键词和向量检索，再用重排序模型判断候选片段的相关程度。这里没有一种方法可以天然保证正确。一个相似度高的旧文档，可能在语义上很接近，却已经不适用于当前版本。

## P15 一条知识库链路，有不止一个出错点

知识库问答看起来是上传文档再提问，背后通常有一条处理链路。首先切分文档，尽量让每个片段保留足够上下文，例如标题、章节和适用版本。然后建立索引，供后续检索使用。

收到问题以后，系统检索候选片段，也可以进一步重排序，再选出适合放进上下文的资料，最后生成回答并关联来源。这里是一种常见流程，具体系统不一定每个步骤都相同。

如果 VPN 问题答错了，可以沿着这条链排查。是不是文档没更新？是不是一句话被切断，条件和结论分到了两个片段？是不是相关文档检索到了，却没有进入最终上下文？还是模型看到资料后仍然理解错了？把这些情况分开，改进才有方向。不能把所有知识库问题都归结为模型不够大，或者提示词不够长。

## P16 Prompt、RAG、微调怎样选择？

这三个词很容易混。Prompt 主要是在本次任务里把目标、规则和示例说明白。RAG 是把外部资料找出来，提供给模型。微调则是通过训练调整模型参数，改善某类任务或者输出行为。

拿 VPN 助手来说，如果输出没有负责人和截止时间，可以先完善提示和结构要求。如果它不知道公司这周更新的远程接入规则，更直接的问题是资料供应。如果我们已经有足够标注样本，希望某类故障分类长期表现得更稳定，可以再评估微调的价值，并用独立样本判断效果。

这些方法可以组合，不是互相替代的三级升级。有了微调也可能还需要查最新资料。有了 RAG 也仍然需要任务要求。另外，上传文档这个动作本身不能说明底层采用了什么：可能直接读取全文，也可能解析和检索。要看应用具体怎么处理。

## P17 Tool Calling：模型提请求，运行环境执行

现在我们让助手从回答问题走向执行任务。Tool Calling 或 Function Calling 的核心是：模型根据工具描述，提出调用哪个工具、提供什么参数；真正执行查询或动作的，是应用或运行环境。

比如我们给模型一个查询 VPN 状态的工具，它可能提出 get_vpn_status，并给出地区参数。运行环境收到后调用对应系统，把正常、异常或者错误结果返回。模型再根据结果决定下一步。某些平台也提供服务端工具，这时执行发生在服务端环境，基本区别仍然是提出请求与实际执行分开。

为什么这个区分重要？因为模型说“我已经查过”并不够。我们需要有工具调用和返回结果。创建工单更明显：生成一个调用请求，还不等于系统已经创建工单；有成功返回和工单编号，才有相应的完成依据。

## P18 Workflow 与 Agent：谁决定下一步？

Workflow 和 Agent 的区别，我们先用一个问题理解：下一步主要由谁决定？Workflow 的主要步骤和分支预先由程序定义，比如分类之后检索，再回答，无法回答就转人工。每个步骤里面仍然可以使用大模型。

Agent 则让模型根据目标和执行反馈，在一定范围里选择下一步。比如服务状态正常，就继续检查配置；服务异常，就按流程报障。它可以重复查询、调整方向，也需要有明确的任务边界。

实际产品经常组合两者。外面是稳定的报障流程，里面的一段排查由模型动态组织。并不是叫 Agent 就更高级，也不是步骤越多就越有效。动态决策带来灵活性，也可能带来更多调用、等待和不稳定性。我们的任务如果用一次调用或者一条固定流程就能做好，就可以从那里开始。

## P19 MCP 连接能力，Skill 复用做事方法

接下来两个经常和 Agent 一起出现的词是 MCP 和 Skill。MCP 是 Model Context Protocol，模型上下文协议，可以帮助 AI 应用以统一方式连接外部工具、资源等能力。比如把现有工单 API 封装成一个 MCP 服务，让支持这个协议的应用接入。

它解决的是连接规范，不会替我们自动写出工单系统，也不会自动授予业务权限。后面的业务接口和授权仍然要真实存在。

Skill 这个词有不同产品用法，这里按 Agent Skills 格式理解：它是一份可复用的任务说明包，可以附带脚本、模板和参考资料。比如整理 IT 报障时，需要收集哪些信息、怎样分类、什么时候升级处理。它告诉助手做事的方法，执行能力仍由实际工具和运行环境提供。两者可以配合，但职责不相同。

## P20 走一遍：查资料 → 查状态 → 创建工单

【演示约三分钟】现在把前面所有组件串起来。用户明确要求帮忙排查，并且服务异常时替他报障。我们先点第一步，知识库找到了远程接入指南，告诉助手应该先看客户端状态，再查服务状态。

第二步，模型提出状态查询，工具返回服务异常。第三步，必要信息已收齐，而且用户已经要求在这个条件下报障，于是模型提出创建工单，运行环境按授权范围执行。第四步，我们核对结果，返回中有工单编号和 created 状态，助手才能据此告诉用户已经创建。

这页是离线教学模拟，没有连接公司系统，也没有产生真实工单。我们演示的是消息和结果怎样流转。现场可以追问：如果第三步只返回错误呢？那么当前只能报告创建失败或者尚未确认，不能说已完成。同样，工单创建成功只证明报障完成，不代表 VPN 故障已经修复。

## P21 API、SDK、流式输出：应用怎样接入模型？

应用通过 API 向模型服务发送请求，再接收结果。SDK 可以理解成对这些接口的代码封装，让开发者不用每次自己处理所有请求细节。模型服务返回的内容，可能是普通文本，也可能是结构化数据或工具调用请求。

流式输出就是在生成过程中逐步接收结果，用户能先看到前面的内容，不必等整段生成结束。但它不一定减少完整生成所需的时间，更不代表业务动作已经做完。

我们要区分三个时刻：首个可见结果什么时候出现，完整回答什么时候生成完，任务什么时候真正完成。有些系统先显示一句“正在查询”，之后才检索和调用工具。第一句话看起来很快，工单编号却可能还要等一段时间。比较体验时，应把指标对应到用户关心的结果。

## P22 算整条任务的账，别只看最后一句话

一次简单摘要可能只需要一个模型请求。我们的 IT 助手可能先生成查询请求，读完状态以后再生成工单请求，最后看到结果再回复用户。具体需要几次取决于实现，这里的三到五次只是教学示意，不是固定规则。

计费也要看具体服务。常见项目有输入和输出 Token，一些服务还区分缓存读取、缓存写入或者推理用量。不要把不同接口的计量口径直接混在一起。历史消息如果被反复带入，也可能反复产生输入用量。

另外还有请求数、Token 吞吐和并发限制。即使单次调用不贵，用户同时上来，也可能排队或者遇到限流。对业务更有意义的比较，是成功完成一个任务总共花多少、等多久；如果一个方案更便宜，却经常需要人工返工，实际收益未必更高。

## P23 评测：用三类真实问题，看系统会不会做对

两个模型都能流畅回答，怎样选？公开 Benchmark 可以作为能力参照，但不能替代我们的业务评测。它未必用我们的文档，未必连接我们的系统，也未必覆盖我们的失败情况。

先准备一组真实、可以判定结果的问题。比如 VPN 配置问题，应该按有效版本的文档回答；服务是否异常，应该查询实时状态；缺少报障必填字段时，应该先补信息，不能自己编。还要加入检索不到、资料过期和工具失败等情况。

比较时尽量固定问题、资料和工具条件，记录结果与失败原因，再看正确率、来源支持、工具成功率、稳定性、延迟和成本。小样本可以帮助发现明显问题，但不能据此宣称所有场景都可靠。评测对象也不仅是一个模型，而是完整应用能否满足任务要求。

## P24 托管 API 还是本地部署？回到实际约束

部署方式也不要只按一个标签决定。托管 API 通常能减少自己维护模型推理基础设施的工作，但需要核对数据使用规则、网络条件、服务限额和长期费用。本地或者自管部署可以更直接地控制部署位置，但硬件、性能、升级和运维工作也要自己承担。

本地部署并不自动解决所有数据访问问题，应用还会连接资料和工具；开放权重也不等于没有使用限制，许可证需要单独看。另一方面，托管 API 也不能仅凭名称就推断数据会怎样保存或使用，要看具体条款和配置。

把这些条件列清楚以后，再用前一页的业务样本比较效果、延迟和完整成本。选择可以很务实：先用满足当前约束的简单方案，把任务做对，再根据实际瓶颈调整。

## P25 把今天的词，放回同一张应用图里

现在把这些词放回同一个应用里。用户在界面上提问，流程或者 Agent 组织任务，通过 API 调用模型。本次 Prompt 和上下文决定模型实际看到哪些信息。

左边是资料与记忆：聊天记录和长期记忆由应用保存、按需要回取；RAG 检索内部资料，Embedding 可以参与语义检索。右边是执行能力：Tool Calling 把模型的调用请求交给运行环境，MCP 可以规范外部连接，Skill 可以提供这类任务的工作方法。

模型参数提供基础能力，外围组件把它变成可用产品。最后再用评测检查是否做对，用任务级的用量和等待时间检查是否划算。以后再听到某个新名词，可以先问它在这张图中的位置：它提供模型能力、补充信息、执行动作，还是组织过程？位置找到了，术语通常就更容易理解。

## P26 带走五句话，再聊你的使用场景

最后带走五句话。第一，应用体验包含模型之外的组件。第二，聊天记录、上下文和记忆不能混成一个概念。第三，既要把任务说清楚，也要把必要资料提供正确。第四，模型提出操作和系统实际执行是不同状态。第五，用真实任务看效果，用整条任务看成本。

接下来留十分钟交流。大家可以挑一个实际问题：是长对话忘记了要求，是知识库没有找到内容，是接口调用失败，还是结果看着合理却没法验证。我们尽量把问题放回刚才的应用图中，看它属于哪一层，需要补什么证据。后面两页附录放了常见延伸词汇，有人感兴趣时可以再翻出来。

## P27 看到模型名字与部署参数，先认这些词

这一页按兴趣讲，不计入主线时间。参数量表示模型中的参数数量，B 表示十亿。Dense 是稠密模型，MoE 是混合专家模型，讨论后者时要区分总参数和每次计算涉及的激活参数。

开放权重说明权重能够获得，具体允许什么用途还要看许可证。量化是使用较低数值精度的表示方式，常用于减少存储和运行资源开销，实际效果要看具体方案。显存除了放权重，也会用于运行时数据，所以不能只看模型文件大小就推断能否顺畅运行。蒸馏则是利用教师模型的输出或其他训练信号来训练学生模型。这些词帮助我们读懂规格，但都不能单独替代业务评测。

## P28 训练、缓存与应用边界的延伸词汇

SFT 是监督微调，使用带有期望输出的训练示例。RLHF 是从人类反馈中进行强化学习，是后训练的一类方法，并不是所有后训练的统称。LoRA 是低秩适配，用较少的可训练参数调整模型。

Transformer 是常见模型架构，Attention 是其中处理信息关联的重要机制。KV Cache 保存注意力计算中的键值状态，避免生成后续内容时重复做全部相关计算；Prompt Cache 是服务提供的输入前缀等缓存能力，内部实现和计费要看具体服务。两者不是完全互不相关，但讨论时应分清所在层次。

最后是提示注入和数据权限。检索资料可能夹带试图改变任务的指令，不能因为它被查到了就把它当成高优先级要求。资料访问与工具执行也需要受到实际授权约束。这些边界与前面所说的“有来源”和“能调用工具”是同时存在的。
